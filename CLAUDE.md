# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Qué es esto

Un daemon Python que convierte una Elgato Stream Deck física en un mando de seguimiento de hábitos y tareas. Corre 24/7 como servicio systemd en una Raspberry Pi 3, sondea la base de datos vía PostgREST cada 15 minutos y navega por un **menú de pantallas** (ver [Menú y pantallas](#menú-y-pantallas)): la vista por defecto "Hoy" pinta hábitos en blanco (pendiente) o gris oscuro (hecho hoy), registrando un checkin al pulsarlos, y tareas pendientes en el color de su prioridad, pasando al mismo gris al pulsarlas — ni un hábito hecho ni una tarea cerrada desaparecen ni mueven ninguna otra tecla, solo cambian de color hasta el siguiente refresco real (**estándar del proyecto para cualquier "check"**, ver [Completar no hace desaparecer](#completar-no-hace-desaparecer)); desde el menú también se llega a vistas filtradas ("Hábitos" —  donde pulsar un booleano ya hecho lo **deshace**, y desde donde su tecla 1 abre "Secciones" — mismo comportamiento que "Hábitos" pero solo con los hábitos de una sección de `habits-core`, ver [Secciones](#secciones) —, "Tareas" — cuya tecla 1 abre igualmente "Proyectos", mismo mecanismo que "Secciones" pero filtrando tareas por proyecto, ver [Proyectos](#proyectos)), a "Logs" (hábitos de solo registro, sin objetivo — uno de registro único diario pasa a gris al registrarse hoy, uno acumulable enseña un contador y nunca pasa a gris — ver [Vista "Logs"](#vista-logs)), a "Crear" (crea una tarea a partir de una plantilla) a "Cronómetros" (etiquetas rápidas tipo Toggl Track: una tecla por etiqueta que alterna iniciar/detener — ver [Vista "Cronómetros"](#vista-cronómetros)), a "TickTick" (PoC deliberadamente ajena a `habits-core`: botones de proyecto y tareas sueltas de una cuenta de TickTick, tap en un proyecto para ver sus tareas, tap en una tarea para completarla y tap sobre una ya gris para reabrirla — ver [Vista "TickTick"](#vista-ticktick)) y a un submenú "Sistema" con la suspensión de la pantalla y el apagado de la Pi. **Mantener pulsado** un hábito o una tarea (en vez de soltarlo enseguida) abre su **menú de opciones**: el de un hábito ya permite deshacer un paso, el de una tarea permite omitirla, cambiar su prioridad o iniciar/detener su cronómetro — ver [Menú de opciones de un hábito/tarea (mantener pulsado)](#menú-de-opciones-de-un-hábitotarea-mantener-pulsado). Dentro de "Secciones", mantener pulsada una sección abre sus propias opciones, con un botón para fijarla/quitarla como botón directo del menú principal — ver [Secciones](#secciones). "Proyectos" (tecla 1 de "Tareas") tiene el mismo mecanismo de fijar/quitar del menú principal — ver [Proyectos](#proyectos). Tras `STANDBY_SECONDS` sin pulsar nada (o pulsando "Suspender") entra en **stand by**: apaga la retroiluminación y deja de sondear, y cualquier tecla lo despierta — ver [Stand by](#stand-by).

La base de datos vive en el repo hermano `../habits-core` (repositorio Git independiente). Este daemon es deliberadamente **tonto**: no calcula qué día es hoy, ni el siguiente valor de un hábito, ni qué tareas tocan, ni si algo está bloqueado. Todo eso lo decide la base. Ver [../CLAUDE.md](../CLAUDE.md) para el contexto que atraviesa ambos repos.

**No hay tests automatizados ni lockfile de dependencias, y nada de esto se ejecuta en la máquina de desarrollo**: no tiene Python usable (solo el stub de la Microsoft Store) ni el hardware. Todo se verifica en la Pi por SSH — ver [Operar la Raspberry Pi](#operar-la-raspberry-pi).

## Arquitectura

Tres capas por carpeta, con una regla de dependencia estricta: **`provider/` no sabe nada del Stream Deck; `deck/` no sabe nada del proveedor de datos; `core/` y `orchestrator.py` orquestan ambos hablando solo con abstracciones.** `orchestrator.py` y `config.py` viven en la raíz porque los comparten las tres capas (el primero es además el `ExecStart` de systemd).

El eje del diseño es un **puerto/adaptador (hexagonal)**: `provider/base.py` define los puertos abstractos y Supabase es solo un adaptador detrás de ellos. Cambiar de backend = escribir otro `HabitProvider`/`TaskProvider`/`TemplateProvider`/`TimerProvider` y tocar **una línea** en `orchestrator.main()` (`SupabaseProvider()`); ni `core/`, ni `deck/`, ni el resto del orquestador cambian.

### `provider/` — la API tras cuatro puertos

- **`base.py`** — los **puertos**. Contiene todo lo que el resto del proyecto necesita saber de "la API", sin acoplarse a ningún backend:
  - **`HabitProvider`** (ABC): `get_habits() -> list[Habit]` (ya trae el progreso de hoy, solo hábitos con objetivo), `get_log_habits() -> list[Habit]` (hábitos de solo registro, `LogHabit`, ver [Vista "Logs"](#vista-logs) — lectura separada de `get_habits()` a propósito, para no cambiar esa interfaz), `step(habit) -> float` (avanza un paso, devuelve el nuevo total), `undo(habit) -> float` (retrocede: booleano → `0`, cuantificable → `value - step` sin bajar de 0; devuelve 0 si hoy no había nada que deshacer, así que repetirlo es seguro — genérico para cualquier `Habit`, lo usa tanto el tap-undo de "Hábitos" como "Deshacer" en el menú de mantener pulsado) y `set_value(habit, value) -> float` (fija el valor exacto de hoy — la usa un hábito `manual_entry` tras teclearlo en la pantalla de teclado numérico, ver [Menú y pantallas](#menú-y-pantallas)).
  - **`TaskProvider`** (ABC): `get_tasks() -> list[Task]` (solo pendientes, **ya ordenadas** por el proveedor), `complete_task(task) -> None`, `skip_task(task) -> None` (marca la ocurrencia como omitida, sin devolver nada; sale de `get_tasks()` igual que al completarla) y `set_priority(task, priority) -> None` (cambia la prioridad de una ocurrencia pendiente, sin devolver nada). Las tres últimas comparten forma con `complete_task`; las usa el menú de opciones de una tarea. Está **separado a propósito** de `HabitProvider`: son dos capacidades distintas y un backend puede ofrecer una sin la otra.
  - **`TemplateProvider`** (ABC): `get_templates() -> list[Template]` (solo las de creación rápida, ya ordenadas) y `create_task(template) -> str` (devuelve el id de la ocurrencia nueva). Separado por la misma razón.
  - **`TimerProvider`** (ABC, ver [Vista "Cronómetros"](#vista-cronómetros)): `get_timer_labels() -> list[TimerLabel]` (solo las de acceso rápido, ya ordenadas), `get_running_timer() -> RunningTimer | None` (el cronómetro en marcha, o nada — a lo sumo uno), `get_daily_totals() -> dict[str, int]` (segundos acumulados hoy, `id de tarea/etiqueta -> segundos`; ausente = 0), `get_task_totals() -> dict[str, int]` (segundos acumulados de SIEMPRE, `task_id -> segundos`, sin filtrar por día; ausente = 0), `toggle_task_timer(task) -> None` y `toggle_label_timer(label) -> None` (alternan el cronómetro de una tarea/etiqueta; ninguna devuelve nada útil, el llamador siempre refresca). Separado por la misma razón que los otros tres. `SupabaseProvider` implementa los cuatro porque salen del mismo contrato.
  - **Excepciones agnósticas**: `ProviderError` → `ProviderAuthError`, `ProviderNetworkError`, `ProviderDataError`. Compartidas por los cuatro puertos, así que `core.health` y el pintado de errores sirven igual para todos.
  - **`Habit`** (ABC), construido desde campos ya parseados, **no** desde JSON crudo: `id`, `name`, `emoji`, `order` (pista para asignar teclas), `current_value` (progreso de hoy, **puede superar `goal`** — 10/8 es válido), `manual_entry` (default `False`, vive en la clase base para que `core.screens` lo lea sin `isinstance`), `section_name` (default `""`, nombre de la sección resuelto por `v_today_habits` — `left join habit_sections` en `../habits-core` — mismo criterio que `manual_entry`: en la clase base para que una sección, ver [Secciones](#secciones), la lea sin `isinstance`); propiedades `goal` (default `1.0`) e `is_done` (`current_value >= goal`, que **solo decide el color de la tecla, no bloquea nada**); `display_label()` abstracto. `BooleanHabit` → muestra el nombre. `RealHabit` (cuantificables, con `goal`/`step`/`unit`) → muestra solo el progreso (`"3/8 Cups"`, o `"10/8 Cups"` por encima del objetivo, sin decimales feos en enteros), **salvo si `manual_entry` es `True`** (p.ej. "Peso"): ahí no hay "progreso hacia un objetivo" que enseñar — el valor es una medición, no un avance — así que se comporta como `BooleanHabit` y muestra el nombre, sin número; el valor se ve al pulsar, en el teclado numérico. Si `manual_entry` es `True`, pulsar la tecla tampoco suma `step`: abre el teclado numérico (ver [Menú y pantallas](#menú-y-pantallas)). `LogHabit` (hábitos de solo registro, ver [Vista "Logs"](#vista-logs)) tiene además `color` (`"#RRGGBB"` o vacío) y `cumulative`/`unit`: si `cumulative` (viene de `type == "Real"`) y hay progreso hoy, `display_label()` añade un contador (`"Cocacola x3"`); si no, solo el nombre — nunca usa `goal`/`is_done`.
  - **`Task`** — concreta y sin subtipos, al revés que `Habit`. Campos: `id` (el de la **ocurrencia**, es lo que se envía para cerrarla), `title`, `emoji`, `priority` (solo `0`/`1`/`3`/`5`, no son contiguos), `overdue` (arrastra de un día anterior), `due_day`, `template_id` (vacío si es tarea única; lo usa "Crear" para saber qué plantillas ya tienen ocurrencia abierta), `timer_running`/`total_seconds` — **mutables, y no vienen del backend**: los calcula `core.screens._mark_running_task` cruzando contra `RunningTimer`/`get_task_totals()`, igual que `Template.has_pending`; los usa `deck.renderer.render_task` para pintar el marco de aviso y anteponer el acumulado de siempre al título (ver [Vista "Cronómetros"](#vista-cronómetros)) — y `completed` (default `False`, **mutable**, mutado de forma optimista por `orchestrator.press_task` tras un `complete_task` con éxito, nunca por el backend: `get_tasks()` solo trae pendientes). `completed` es el campo que aplica el estándar del proyecto para cualquier "check" (ver [Completar no hace desaparecer](#completar-no-hace-desaparecer)): pinta la tecla en gris sin sacar la tarea de la lista, mismo papel que `Habit.is_done` para un hábito y que `ticktick.base.TickTickTask.completed` para TickTick — a diferencia de ese último, aquí no hay forma de revertirlo desde el deck (habits-core no expone una RPC de "descompletar" tarea), así que pulsar una tarea ya gris no hace nada. `display_label()` devuelve el título recortado a `TITLE_MAX_CHARS` con elipsis. **La base no guarda icono de tarea**, pero es habitual escribir el emoji dentro del título (`"Bano 🚽"`): `build_task` lo separa a `emoji` para pintarlo como icono a color, igual que el `icon_res` de un hábito. El color de la tecla lo sigue dando la prioridad, salvo completada (gris).
  - **`Template`** — la definición reutilizable de una tarea que se repite **sin momento fijo** ("Cita peluquero"). Campos: `id` (el de la **plantilla**, no el de la tarea que se crea), `title`, `emoji` (mismo criterio que `Task`), `priority`, y `has_pending` — **mutable, y no viene del backend**: lo calcula `core.screens._create_items` en cada resolución cruzando plantillas con tareas pendientes. Al revés que una `Task`, una plantilla **no desaparece** al usarla.
  - **`TimerLabel`** — la etiqueta rápida de cronómetro, mismo papel que `Template` pero para cronómetros: `id`, `name`, `emoji`, `order`, y `running`/`started_at`/`today_seconds` — **mutables, y no vienen del backend**: los calcula `core.screens._timer_items` cruzando etiquetas con `RunningTimer`/`get_daily_totals()`, igual que `Template.has_pending`. `display_label()` devuelve el nombre recortado; el tiempo transcurrido (o el total del día, si está parada) lo añade `deck.renderer.render_timer`, no esta clase.
  - **`RunningTimer`** — el cronómetro en marcha ahora mismo (o nada), sale de `get_running_timer()`. Campos: `id`, `task_id`/`label_id` (mutuamente excluyentes, vacío el que no aplique), `title` (ya denormalizado por la base, sin `join`), `started_at` (ISO 8601 con offset — única fuente para calcular tiempo transcurrido, nunca un contador que incrementa en el cliente).
- **`supabase.py`** — el **adaptador**; concentra todo lo específico del backend:
  - Lee `SUPABASE_URL` y `SUPABASE_PUBLISHABLE_KEY` del `.env`; `__init__` lanza `ProviderAuthError` si falta alguna. Base PostgREST `<url>/rest/v1`, cabeceras `apikey` + `Authorization: Bearer`.
  - `get_habits`: **una sola petición** a `v_today_habits` (la vista ya filtra activos y trae el progreso), con `order=sort_order` porque la vista no ordena por sí sola.
  - `get_log_habits`: **una sola petición** a `v_log_habits` (`purpose='log'`, nunca "pendientes"), pidiendo también `type`/`unit` (que la vista ya expone) para que el cliente decida `LogHabit.cumulative` — ver [Vista "Logs"](#vista-logs). Tampoco ordena por sí sola.
  - `step`: `POST /rpc/habit_step` con `{"p_habit_id": habit.id}`. Atómico en la base (Boolean → salta a `goal`; Real → suma `step` sin tope, agnóstico de `purpose` — es lo que hace que un log `type='Real'` acumule por día igual que un hábito con objetivo). Devuelve el nuevo total.
  - `undo`: `POST /rpc/habit_undo`, mismo cuerpo y mismo tratamiento de respuesta que `step`. Lo dispara la vista "Hábitos" sobre un booleano ya hecho (ver [Menú y pantallas](#menú-y-pantallas)) y, de forma genérica para cualquier hábito, "Deshacer" en el menú de mantener pulsado (ver [Menú de opciones de un hábito/tarea](#menú-de-opciones-de-un-hábitotarea-mantener-pulsado)).
  - `set_value`: `POST /rpc/habit_set` con `{"p_habit_id": habit.id, "p_value": value}`. La base hace `greatest(p_value, 0)` y fija (no suma) el checkin de hoy; devuelve el nuevo total, mismo tratamiento de respuesta que `step`/`undo`. Solo lo dispara confirmar ("OK") en la pantalla de teclado numérico de un hábito `manual_entry`.
  - `get_tasks`: **una sola petición** a `v_today_tasks`, que ya excluye completadas y omitidas y arrastra las vencidas. Tampoco ordena por sí sola: el orden va explícito en `_TASKS_ORDER` (`priority.desc,due_date.asc`).
  - `complete_task`: `POST /rpc/complete_task` con `{"p_task_id": task.id}`. La función devuelve `void`, así que responde **204 sin cuerpo**: no hay JSON que parsear y el status es toda la confirmación. Es idempotente en la base, reintentar es seguro.
  - `skip_task`: `POST /rpc/skip_task` con `{"p_task_id": task.id}`. Misma forma que `complete_task` (`void`, 204 sin cuerpo, idempotente). RPC preexistente del contrato (ya usada por otros clientes), así que añadir esta opción al deck no tocó `habits-core`.
  - `set_priority`: `POST /rpc/set_task_priority` con `{"p_task_id": task.id, "p_priority": priority}`. Misma forma que `complete_task` (`void`, 204 sin cuerpo). La RPC solo toca ocurrencias pendientes; sobre una ya completada/omitida o inexistente no hace nada, ni falla.
  - `get_templates`: **una sola petición** a `v_templates` con `show_in_deck=eq.true`. La vista devuelve todas las plantillas activas (también las que materializará `pg_cron`, que aquí no se pintan) y **el filtro es del cliente a propósito**: así la PWA sigue viendo la lista completa con el mismo `grant`, sin necesidad de una vista nueva.
  - `create_task`: `POST /rpc/instantiate_task` con `{"p_template_id": template.id}`. **No manda fecha** — sin `p_due` la base hace vencer la ocurrencia ahora, que es lo que la hace aparecer en `v_today_tasks`; si mandara `null` explícito nacería invisible. Al contrario que `complete_task`, devuelve el `uuid` nuevo (200 **con** cuerpo JSON, hay que parsearlo), y **no es idempotente**: dos llamadas, dos tareas.
  - `get_timer_labels`: **una sola petición** a `v_timer_labels` con `show_in_deck=eq.true`. Mismo patrón que `get_templates`: filtro del cliente a propósito.
  - `get_running_timer`: **una sola petición** a `v_running_timer` con `limit=1`. `None` si la lista viene vacía; si no, `build_running_timer(raw[0])`.
  - `get_daily_totals`: **una sola petición** a `v_timer_daily_totals`. Cada fila trae `task_id` XOR `label_id` (garantizado por la base): el id no nulo de cada fila basta como clave del dict resultado, sin distinguir de qué tabla viene.
  - `get_task_totals`: **una sola petición** a `v_task_timer_totals` (solo `task_id`, sin `label_id`: una etiqueta no tiene "acumulado de siempre" en el contrato).
  - `toggle_task_timer`/`toggle_label_timer`: ambas `POST /rpc/timer_toggle`, con `{"p_task_id": task.id}` o `{"p_label_id": label.id}` respectivamente (la RPC exige exactamente uno de los dos, PostgREST usa el `default null` del otro). Misma forma que `complete_task` (`void`, 204 sin cuerpo). La base decide start-vs-stop mirando su propio estado, nunca lo que el cliente asuma.
  - Traduce `RequestException` / 401-403 / no-2xx / JSON inválido a las excepciones `Provider*`. Un 401/403 puede ser clave inválida **o** un `GRANT` que falta en el contrato; el mensaje lo insinúa.
  - `build_habit(data)`: parsea `icon_res` (`"txt_<emoji>"` → emoji vía `core.emoji.extract_emoji`; los predefinidos tipo `"habit_water"` dan emoji vacío), enruta `type == "Real"` a `RealHabit` (con `manual_entry` de la columna homónima) y todo lo demás (incluido `"Boolean"` y valores desconocidos) a `BooleanHabit`, toma `order` de `sort_order`. `build_log_habit(data)` es el equivalente para `v_log_habits`: siempre construye `LogHabit` (sin ramas de clase por `type`, un log nunca cambia de clase), pero sí usa `type` para fijar `cumulative` (`"Real"` → `True`). `build_task(data)` es el equivalente para tareas, sin ramas: la vista solo devuelve pendientes. `build_timer_label(data)` es el equivalente para etiquetas de cronómetro (emoji sacado de `name`, sin ramas). `build_running_timer(data)` mapea `v_running_timer`: `title` ya viene denormalizado desde la base, pero **sí** extrae y descarta el emoji si lo llevaba (esta pantalla no tiene icono propio donde pintarlo, al revés que `build_task`/`build_timer_label`).
  - Las tablas (`habits`, `habit_checkins`, `tasks`, …) están cerradas con RLS y no son accesibles con la clave publishable: este adaptador nunca las menciona. El contrato está en `../habits-core/docs/contrato.md`, el porqué de la regla en `../habits-core/docs/estructura-bd.md` y peticiones de ejemplo listas para lanzar en `../habits-core/tools/supabase.http`.

### `deck/` — hardware y pintado

- **`session.py`** — `DeckSession`: apertura (30 reintentos cada 2s; `sys.exit(1)` si no aparece), cierre, `reconnect()` y brillo (`set_brightness()`, entre `BRIGHTNESS = 60` y `BRIGHTNESS_STANDBY = 0`). `reconnect()` solo se usa tras un fallo en marcha, nunca en el arranque inicial, y **reabre siempre a `BRIGHTNESS`**: por eso el bucle principal re-aplica el brillo de stand by tras reconectar (ver [Stand by](#stand-by)).
- **`renderer.py`** — alto nivel, sobre una tecla o el deck completo: `render_habit` (usa `display_label()`, `emoji` e `is_done` para elegir blanco/pendiente o gris/hecho — solo color, sin bloquear `COLOR_TASK_TIMER_BORDER_HIGH_PRIORITY` para no fundirse con el fondo ya rojo — ver [Vista "Cronómetros"](#vista-cronómetros)), `render_task_sending` (verde vivo + ✔, el acuse de recibo de la pulsación), `render_checkin_error`, `render_empty`, `render_menu_key` (tecla 0, fija en toda pantalla), `render_arrow` (teclas 5/10: el icono ◀️/▶️ se pinta siempre, activa o no la paginación — solo ## Menú y pantallas

La tecla 0 (`config.KEY_MENU`) abre siempre el menú principal, desde cualquier pantalla (no hace nada si ya estás en el menú). El menú tiene botones "Hoy", "Hábitos", "Tareas", "Crear", "Logs", "Cronómetros" (fija en la tecla 8) y "Sistema" (fija en la 14); "Sistema" es un submenú con "Suspender" y "Apagar" — sin botón "Atrás": sería redundante, la tecla 0 ya vuelve al menú principal desde Sistema igual que desde cualquier otra pantalla. Las secciones no tienen entrada aquí a propósito: el único acceso es la tecla 1 de "Hábitos" (ver [Secciones](#secciones)), para no duplicar el camino. La vista por defecto, tanto al arrancar el daemon como al volver por inactividad o del stand by, es "Hoy" (`core.screens.DEFAULT_VIEW_ID`).

### Completar no hace desaparecer

**Estándar del proyecto, obligatorio para cualquier feature nueva que "complete" algo** (marcar un hábito, cerrar una tarea, o lo que sea análogo en el futuro): el elemento pulsado **nunca** se saca de la lista ni desaparece de la tecla en el momento de pulsarlo. Se pinta en gris (`deck.style.COLOR_HABIT_DONE`/`COLOR_TEXT_HABIT_DONE`, el mismo par en los tres casos de abajo) y se queda exactamente en su misma tecla hasta que un **refresco real** (no un repintado optimista) deje de traerlo. Nunca se recoloca el resto de teclas por esto.

**Por qué.** Antes de esto, "Hoy" ocultaba un hábito hecho o una tarea cerrada al instante y recolocaba todo lo que quedaba una posición hacia "arriba" (hacia la tecla más baja libre). Eso tiene un coste real: si pulsas por error, el elemento ya no está donde lo viste para deshacerlo, y lo que ocupó su sitio es otra cosa distinta — fácil de pulsar sin querer justo después de la primera pulsación. Manteniendo la tecla fija se resuelven las dos cosas a la vez: lo que acabas de pulsar sigue ahí (gris) para poder revisarlo o deshacerlo, y ninguna otra tecla cambia de contenido por tu culpa.

**Cómo está implementado hoy** (tres casos, mismo patrón en los tres):

- **Hábito** (`provider.base.Habit.is_done`, ya existía desde el principio): `core.screens._today_items`/`_tiered_page_builder` incluyen SIEMPRE el hábito, hecho o no — nunca se filtra por `is_done`. `deck.renderer.render_habit` decide el color mirando `is_done` en cada repintado. "Hoy" y "Hábitos" además dejan deshacer con un tap corto sobre un booleano ya hecho (`ViewSpec.allows_undo`, ver más abajo) — un cuantificable nunca deshace, sigue sumando por encima del objetivo.
- **Tarea de habits-core** (`provider.base.Task.completed`, nuevo campo): a diferencia de un hábito, el backend nunca envía una tarea completada (`get_tasks()` solo trae pendientes), así que `completed` es **puramente optimista**: `orchestrator.press_task` lo pone a `True` tras un `complete_task` con éxito, sin sacar la tarea de `tasks_ref`. `core.screens._today_items`/`_tasks_items`/`_project_page` tampoco filtran por `completed`; `deck.renderer.render_task` pinta gris si `task.completed`. `core.screens.resolve_press` sí bloquea una segunda pulsación (`PressAction("noop")`, mismo criterio que una plantilla con ocurrencia pendiente): **no hay forma de deshacer un cierre desde el deck** todavía — habits-core no expone una RPC de "descompletar" tarea (al contrario que los hábitos, que ya tienen `habit_undo`). Si hace falta en el futuro, es una RPC nueva en `../habits-core` (proceso develop→test→main, ver `../habits-core/CLAUDE.md`) más un `uncomplete_task` en `TaskProvider`, mismo mecanismo que TickTick (ver abajo). Solo la siguiente lectura real de tareas hace desaparecer de verdad una tarea completada: reemplaza `tasks_ref` entero con lo que devuelva `get_tasks()`, que ya no la trae.
- **Tarea de TickTick** (`ticktick.base.TickTickTask.completed`, ver [Vista "TickTick"](#vista-ticktick)): el caso original que inspiró este estándar, y el único de los tres con undo real -- `uncomplete_task` SÍ existe (sin documentar oficialmente, pero validado a mano). Pulsar una tarea de TickTick ya gris la reabre en vez de no hacer nada.

**Qué queda fuera a propósito**: omitir (skip) una tarea (`orchestrator.press_task_skip`) sigue sacándola de `tasks_ref` al instante, sin gris intermedio — solo se llega ahí desde el menú de mantener pulsado, no con un tap normal, así que no hay el mismo riesgo de pulsación accidental que este estándar busca evitar.

**Para una vista/feature nueva**: si pinta hábitos o tareas, inclúyelos en su `items_fn`/`PageBuilder` sin filtrar por `is_done`/`completed` — es lo único que hace falta, el color y el bloqueo de repulsación ya los dan `deck.renderer`/`core.screens.resolve_press` de forma genérica. Si el "check" es sobre un tipo de dato nuevo (ni hábito ni tarea), sigue el mismo patrón: un campo mutable `completed`/equivalente en el objeto de dominio, mutado de forma optimista tras confirmar la escritura, nunca filtrado al listar, pintado en gris por el renderer, y bloqueado en `resolve_press` si no hay forma de revertirlo.

**Tecla 7 del menú: atajo al cronómetro actual** (`core.screens.KEY_TIMER_SHORTCUT`, junto a "Cronómetros" en la 8 a propósito). No es un botón de `MENU_ENTRIES` — no navega a ninguna vista, alterna directamente un cronómetro — así que `core.screens._nav_page` la excluye del reparto automático vía un `reserved_keys` nuevo, sin que ningún `MenuEntry` la ocupe. Pinta siempre algo, nunca queda vacía (`core.screens._timer_shortcut_item`):

- **Corriendo**: rosa (`COLOR_TIMER_RUNNING`), título + tiempo transcurrido, igual que en "Cronómetros" — pulsarla lo para (mismo `rpc/timer_toggle` que cualquier otra tecla de cronómetro).
- **Parado, recordando el último usado**: gris (`COLOR_TIMER_SHORTCUT_IDLE`, no el turquesa de "Cronómetros" — aquí no significa "listo para arrancar", sino "en espera de que lo reactives") con su título, y delante el total acumulado hoy entre corchetes si ya tiene algo (`"[00:25] Lectura"`, ver [Vista "Cronómetros"](#vista-cronómetros)) — pulsarla lo vuelve a arrancar.
- **Sin ningún cronómetro usado todavía** (o el que se recordaba ya no existe): mismo gris, con el aviso "Sin cronómetro" y sin total (su `today_seconds` es siempre 0) — pulsarla no hace nada (el id que lleva, `core.screens._TIMER_SHORTCUT_EMPTY_ID`, no coincide con ninguna tarea/etiqueta real).

El "recuerdo" es `orchestrator.last_timer_ref` — el último `RunningTimer` no vacío visto, actualizado junto a `running_timer_ref` en cada `refresh_cycle` pero que **no** se borra solo porque el cronómetro pare (a diferencia de `running_timer_ref`). Vive solo en memoria del daemon: un reinicio del servicio lo deja vacío hasta que arranque un cronómetro nuevo — cosmético, no afecta a que el cronómetro **corriendo** siempre se lea fresco de la base. `orchestrator._prune_stale_last_timer`, llamada al principio de todo repintado (no solo en `refresh_cycle`, para no depender de esperar hasta 15 min), lo olvida si la tarea ya no está en `tasks_ref` o la etiqueta ya no está en `timer_labels_ref` (completada, omitida, archivada) — la tecla 7 vuelve sola al aviso "Sin cronómetro". `press_timer_toggle` tiene el mismo chequeo como red de seguridad ante una carrera rara (pulsar justo en el instante en que se volvió obsoleto): si no encuentra tarea/etiqueta y el id pulsado coincide con lo que recordaba `last_timer_ref`, lo limpia y repinta ahí mismo.

Todo esto se resuelve con una sola abstracción en `core/screens.py`: una pantalla activa (`ScreenState`: menú, Sistema o una vista con su página) se resuelve contra los datos vigentes con `resolve_page(...)` a un `ResolvedPage` (qué hábito/tarea/plantilla/entrada de menú pintar en cada tecla, más el total de páginas), y una pulsación se resuelve con `resolve_press(screen, key, page)` a una `PressAction` que el dispatcher de `orchestrator.py` ejecuta. `deck/renderer.py::render_page` pinta cualquier `ResolvedPage` con el mismo bucle, sea menú, Sistema o una vista.

**Añadir una vista nueva** (p.ej. "por proyecto") es: una función `items_fn(habits, tasks, templates, log_habits, timer_labels, running_timer, daily_totals, task_totals)` que decide qué le toca, una entrada nueva en `core.screens.VIEWS` (usando `_flat_page_builder` si no necesita reutilizar el mapeo estable de hábitos, o `_tiered_page_builder` si sí), **declarando en `ViewSpec.needs` qué lecturas necesita** (ver [Caché de lecturas](#caché-de-lecturas): es lo que hace que entrar en ella pida solo eso, y declararlo de menos significa pintar datos viejos hasta el ciclo periódico) y un botón más en `MENU_ENTRIES`. Todo builder recibe los **ocho** conjuntos de datos aunque casi ninguno los use enteros: es lo que permite cruzarlos (así "Crear" sabe qué plantillas ya tienen ocurrencia abierta, y "Cronómetros" cruza etiquetas contra `running_timer`/`daily_totals`). Nada más del sistema cambia — incluido el deshacer, que es opt-in por vista (`ViewSpec.allows_undo`, ver abajo). La única excepción está fuera de `core/screens.py`: si la vista debe mostrar códigos de error, hay que añadir su `view_id` a las listas literales de `orchestrator._paint_current_screen`.

Las teclas 5 y 10 (`KEY_PAGE_PREV`/`KEY_PAGE_NEXT`) muestran siempre el icono de flecha "◀"/"▶", para que se reconozcan de un vistazo igual que la de menú; el fondo distingue si hacen algo: activo (`COLOR_ARROW`) cuando la pantalla activa (menú, Sistema o una vista) tiene más de `PAGE_SIZE` (12) ítems, neutro (`COLOR_NEUTRAL`) si no. `PAGE_SIZE` es una única constante para todas las pantallas: 5 y 10 nunca han sido teclas de contenido, con o sin más de una página caben 12 ítems por página.

**El teclado numérico es la única pantalla que reinterpreta las teclas reservadas 0/5/10.** Lo abre pulsar, desde "Hoy" o "Hábitos", un hábito cuantificable con `manual_entry = true` en la base (p.ej. "Peso": no tiene sentido ir sumando `step` de 1 en 1, hay que fijar el valor exacto del día). `ScreenState` gana `ScreenKind.NUMERIC_ENTRY` y dos campos, `entry_habit_id`/`entry_value`; al entrar **no se tocan** `view_id`/`page`, así que "Salir" vuelve exactamente a la vista de origen sin necesitar un campo "volver a" aparte. Layout fijo (`core.screens.NUMERIC_KEYPAD`), numeración de fila (5 columnas × 3 filas):

```
Salir    valor   1   2   3
Borrar     0     4   5   6
  OK       .     7   8   9
```

Aquí la tecla 0 es "Salir" (no abre el menú principal), la 5 es "Borrar" (no la flecha "◀") y la 10 es "OK" (no la flecha "▶") — `core.screens.resolve_press` comprueba `ScreenKind.NUMERIC_ENTRY` **antes** que `KEY_MENU`/`KEY_PAGE_PREV`/`KEY_PAGE_NEXT` a propósito, para no arrastrar su significado habitual. Teclear un dígito, el punto o borrar solo muta `entry_value` y repinta (sin red); "OK" con el campo vacío o inválido (p.ej. solo ".") no hace nada, para poder seguir tecleando. Confirmar llama a `HabitProvider.set_value` (`rpc/habit_set`, ver arriba): con éxito, mutación optimista y vuelta a la vista de origen; con fallo, la tecla "OK" queda en rojo con el código y la pantalla se queda en el teclado con lo tecleado intacto, para reintentar sin perder nada (mismo patrón de acuse/fallo que un hábito o una tarea).

Un hábito `manual_entry` **no tiene "deshacer"**: a diferencia de "Hábitos" con un booleano ya hecho, pulsarlo siempre abre el teclado, esté hecho hoy o no — `habit_set` sobrescribe el checkin de hoy, así que re-teclear ya es la corrección. No hay entrada nueva en el menú principal: la única forma de llegar aquí es pulsando un hábito `manual_entry` en "Hoy" o "Hábitos".

Entrar en una vista desde el menú ("Hoy"/"Hábitos"/"Tareas"/"Crear"/"Logs") la pinta **al instante** con los datos ya cacheados y, solo si esos datos están caducados, los relee por detrás — ver [Caché de lecturas](#caché-de-lecturas). Navegar dentro de una pantalla ya cargada (Sistema, cambiar de página) solo repinta, sin mirar siquiera la caché. El refresco periódico de `REFRESH_SECONDS` sigue actualizando los datos en segundo plano y repinta lo que esté visible en cada momento, sea cual sea la pantalla activa.

Si el deck lleva `AUTO_RETURN_SECONDS` (5 min) sin ninguna pulsación estando fuera de "Hoy", vuelve solo a "Hoy" (con los datos ya en caché, sin refetch). Cualquier pulsación, en cualquier pantalla, reprograma ese temporizador — y también el de stand by, ver abajo.

### Menú de opciones de un hábito/tarea (mantener pulsado)

El menú de un **hábito** tiene una opción real: **Deshacer** (tecla 1). El de una **tarea** tiene tres: **Skip** (tecla 1), **iniciar/detener cronómetro** (tecla 2) y **cambiar la prioridad** (teclas 11-14). Ver "Cómo extenderlo" más abajo para añadir opciones nuevas a cualquiera de los dos.

Mantener pulsado un hábito o una tarea (en cualquier vista que los muestre: "Hoy", "Hábitos", "Tareas") en vez de soltarlo enseguida abre `ScreenKind.ITEM_OPTIONS`. **Esto cambia cuándo se ejecuta la acción normal de un hábito/tarea**: ya no es al presionar, es al **soltar** (ver `orchestrator.make_key_callback`):

- Al presionar una tecla que resuelve a `"habit"`/`"habit_undo"`/`"task"`, se arma un temporizador de `config.LONG_PRESS_SECONDS` (0.6 s) en vez de actuar.
- Si se suelta **antes**, se cancela el temporizador y se ejecuta la acción de siempre (paso, deshacer o cierre) — con la latencia típica de un toque humano, imperceptible.
- Si el temporizador **dispara con la tecla todavía pulsada**, abre el menú de opciones para ese hábito/tarea; la liberación posterior de la tecla no hace nada, ya quedó consumida.

Las demás teclas (plantilla, navegación, teclado numérico) no tienen esta espera: siguen actuando al presionar, sin cambios.

`ScreenState` gana `ScreenKind.ITEM_OPTIONS` y dos campos, `entry_item_kind` ("habit"/"task") y `entry_item_id`; igual que `NUMERIC_ENTRY`, entrar **no toca** `view_id`/`page`, así que "Volver" regresa exactamente a la vista/página de origen sin necesitar un campo aparte. **Un hábito y una tarea llevan a pantallas distintas**: `core.screens.resolve_page` elige `HABIT_OPTIONS_LAYOUT` o `TASK_OPTIONS_LAYOUT` según `entry_item_kind` — dos layouts fijos separados a propósito, porque sus opciones futuras serán distintas (una tarea no tiene objetivo, un hábito no tiene fecha de vencimiento). En ambos: tecla 0 = "Volver" (mismo azul de navegación que "Salir" en el teclado numérico — mismo rol: esto te saca de aquí sin tocar nada). `HABIT_OPTIONS_LAYOUT` añade la tecla 1 ("Deshacer", ámbar), el resto vacías; `TASK_OPTIONS_LAYOUT` añade la tecla 1 ("Skip", naranja), la tecla 5 como cabecera ("Prioridad") y las teclas 11-14 con los cuatro colores de prioridad (ver más abajo). Las teclas 0/5/10 **no** se reinterpretan aquí como en el teclado numérico: `resolve_press` resuelve `ITEM_OPTIONS` antes de llegar a esa lógica, así que la tecla 5 puede llevar contenido normal como cualquier otra. `core.screens.resolve_press` comprueba `ScreenKind.ITEM_OPTIONS` **antes** que `KEY_MENU`/paginación, mismo motivo que `NUMERIC_ENTRY`: aquí la tecla 0 no abre el menú principal.

**El menú de un hábito abre igual para cualquier `Habit`**: uno con objetivo (`BooleanHabit`/`RealHabit`, desde "Hoy"/"Hábitos") o uno de solo registro (`LogHabit`, desde "Logs") — `orchestrator._arm_hold` no distingue el tipo, solo si la pulsación resolvió a `"habit"`/`"habit_undo"`. La única opción real hoy, "Deshacer", ya vale para los dos por igual (ver más abajo).

Un hábito `manual_entry` (que ya reinterpreta su propia pulsación para abrir el teclado numérico) queda **fuera** de este mecanismo: `resolve_press` lo resuelve a `"habit_enter_value"`, no a `"habit"`/`"habit_undo"`, así que mantenerlo pulsado no hace nada especial — sigue abriendo el teclado al instante, como siempre.

**Deshacer el progreso de un hábito** (`OptionEntry.kind == "undo"`, tecla 1 de `HABIT_OPTIONS_LAYOUT`, ámbar propio `deck.style.COLOR_NUMERIC_BACKSPACE` — mismo color que "Borrar" en el teclado numérico, mismo significado): resuelve a `PressAction("habit_options_undo")`, sin payload — el id del hábito sale de `screen.entry_item_id`, igual que el resto de esta pantalla. Llama a `HabitProvider.undo()` (`orchestrator.press_habit_undo_option`), la misma operación que ya usa el tap-undo de "Hábitos" pero disponible aquí para **cualquier** hábito, con objetivo o de "Logs" (booleano → `0`, cuantificable → `value - step` sin bajar de `0`) — antes de esto no había ninguna forma de deshacer un hábito cuantificable con objetivo en ningún sitio del deck, ni un log acumulable pulsado de más (ver [Vista "Logs"](#vista-logs)). Éxito → mutación optimista de `habit.current_value`, sale de `ScreenKind.ITEM_OPTIONS` a la vista de origen y **relee los hábitos por detrás** (`refresh_after_write`, ver [Caché de lecturas](#caché-de-lecturas)): igual que el `"habit_undo"` de una pulsación corta normal, el valor que devuelve la base es el del día y en un hábito `weekly_quota` hay que releer el contador semanal real, no fiarse del optimista. Fallo → la tecla queda en rojo con el código, sin salir del menú, mismo patrón que el resto.

**Cambiar la prioridad de una tarea** (`OptionEntry.kind == "priority"`, teclas 11-14 de `TASK_OPTIONS_LAYOUT`, blanco/verde/amarillo/rojo — los mismos colores que `deck.style.COLOR_TASK_BY_PRIORITY`): pulsar una de estas cuatro teclas resuelve a `PressAction("task_set_priority", payload=<prioridad como texto>)`. El id de la tarea **no** va en el payload: `orchestrator._run_action` lo lee de `screen.entry_item_id` en el momento de ejecutar (mismo patrón que `"numeric_confirm"` con `entry_habit_id`/`entry_value`), lo reserva con `_claim`/`_release` como cualquier otra escritura, y llama a `TaskProvider.set_priority` (`rpc/set_task_priority` en `../habits-core`, que solo toca ocurrencias pendientes). Éxito → mutación optimista de `task.priority` + `exit_item_options` (vuelve a la vista de origen, ya con el color nuevo si esa tarea sigue visible ahí). Fallo → la tecla pulsada queda en rojo con el código, sin salir del menú, para poder reintentar sin perder el contexto — mismo patrón de acuse que un paso de hábito o un cierre de tarea.

**Omitir (skip) una tarea** (`OptionEntry.kind == "skip"`, tecla 1 de `TASK_OPTIONS_LAYOUT`, naranja propio `deck.style.COLOR_TASK_SKIP`): resuelve a `PressAction("task_skip")`, sin payload — el id de la tarea sale de `screen.entry_item_id`, igual que el cambio de prioridad. Pulsarla pinta primero el acuse verde de siempre (`render_task_sending`) y llama a `TaskProvider.skip_task` (`rpc/skip_task` en `../habits-core` — **RPC ya existente y ya con `grant` a `anon`**, así que esta opción fue enteramente cliente, sin tocar la base). Éxito → la tarea sale de `tasks_ref` (igual que al completarla) + `exit_item_options`: la vista de origen se repinta ya sin ella. Fallo → mismo patrón de tecla en rojo que el resto.

**Iniciar/detener el cronómetro de una tarea** (`OptionEntry.kind == "timer"`, tecla 2 de `TASK_OPTIONS_LAYOUT`, rosa `deck.style.COLOR_TIMER_RUNNING`/turquesa `COLOR_TIMER_STOPPED` según el estado): a diferencia de las tres opciones anteriores, **sí** lleva el id de la tarea en el payload de la `PressAction` (`resolve_press` lo lee de `entry_item_id` en ese momento) — resuelve al mismo `PressAction("timer_toggle", task_id)` que pulsar directamente una tecla de la vista "Cronómetros" (ver [Vista "Cronómetros"](#vista-cronómetros)), para que ambos orígenes compartan un único camino de ejecución en `orchestrator.press_timer_toggle`. Llama a `TimerProvider.toggle_task_timer` (`rpc/timer_toggle` en `../habits-core`, con `p_task_id`). Éxito → **nunca mutación optimista** (la RPC puede parar un cronómetro distinto del que se pulsó): se releen las tres lecturas de cronómetro (`refresh_after_write(TIMER_RESOURCES)`). **No sale de `ScreenKind.ITEM_OPTIONS`** (a diferencia de "Skip"/"cambiar prioridad"): se queda en el menú, mismo criterio que "Ajustar el progreso" de un hábito real, para poder ver el cronómetro corriendo o volver a pararlo sin reabrir el menú. Fallo → mismo patrón de tecla en rojo que el resto.

Si `running_timer.task_id` coincide con la tarea abierta, `resolve_page` rellena `running`/`started_at` y pone en `label` el título denormalizado de `running_timer` (no "Detener cronómetro"): la tecla pinta `"título\n[tiempo]"`, sin emoji — para saber qué está corriendo leyendo la propia tecla, sin tener que recordarlo. Si no está corriendo, se pinta `label` ("Iniciar cronómetro") con su emoji ▶️, en el tamaño normal de esta pantalla. Ver [Vista "Cronómetros"](#vista-cronómetros) para cómo se mantiene ese tiempo al día sin refrescar a mano.

**Cómo extenderlo**: añadir una opción real es añadir una entrada a `HABIT_OPTIONS_LAYOUT` o `TASK_OPTIONS_LAYOUT` (según a cuál corresponda) con su propio `kind`, darle significado en `core.screens.resolve_press` (un `PressAction.kind` nuevo) y ejecutarla en `orchestrator._dispatch_navigation` si es pura navegación, o con el mismo patrón `_claim`/`_release` + lectura de `screen.entry_item_id` que usan `"task_set_priority"`/`"task_skip"`/`"habit_options_undo"` si toca red — mismo patrón que cualquier otro layout fijo de este módulo (`NUMERIC_KEYPAD`, `STANDBY_LAYOUT`). El elemento sobre el que actuar ya está disponible en `screen.entry_item_kind`/`entry_item_id`.

## Stand by

`ScreenKind.STANDBY` es la quinta pantalla: baja la retroiluminación del deck al mínimo (`session.set_brightness(BRIGHTNESS_STANDBY)`), pinta una pantalla fija con un icono y suspende el ciclo de refresco. Entra de dos formas, ambas por `orchestrator._enter_standby`:

- **Sola**, tras `config.STANDBY_SECONDS` (30 min) sin ninguna pulsación. Es un segundo `_IdleTimer` con el mismo disparador que el de auto-retorno (cualquier tecla los reprograma los dos) y plazo distinto, así que lo normal es que primero vuelva a "Hoy" a los 5 min y 25 min después se apague.
- **A mano**, con el botón "Suspender" del submenú Sistema.

**Es la única palanca de consumo real que tiene el daemon, y es la que importa.** La deck MK.2 declara `MaxPower 500mA` y consume ~300 mA (~1,5 W) en marcha; los 15 backlights son el grueso, así que bajarlos al mínimo ahorra del orden de ~0,7–0,9 W de los ~2,5–3 W del conjunto Pi+deck (a brillo 0 serían ~0,1 W más, que es lo que cuesta ver el icono). Todo lo demás que se probó en la Pi 3 no compensa: `ondemand` ya baja sola a 600 MHz en reposo, el daemon ya consume 0,2% de CPU (bajar `set_poll_frequency` no da nada), y HDMI/LEDs/`wlan0` suman ~0,1–0,3 W a cambio de reglas `sudoers` nuevas. Cortar la alimentación USB o dejar que la deck haga autosuspend USB mataría el propio camino de despertado. **No se puede medir por software**: la Pi 3 no tiene el ADC del PMIC (`vcgencmd pmic_read_adc` responde `Command not registered`, es de Pi 4/5); haría falta un medidor USB intercalado.

**Pulsar cualquier tecla despierta, y esa pulsación no hace nada más.** `core.screens.resolve_press` comprueba `ScreenKind.STANDBY` **lo primero de todo** — antes que `NUMERIC_ENTRY` y antes que `KEY_MENU`/paginación — y devuelve `"wake"` sin llegar a mirar el índice de tecla. Es lo que garantiza que encender el deck a ciegas no cierre la tarea ni marque el hábito que hubiera debajo. Cualquier pantalla nueva que se añada debe respetar ese orden.

Despertar (`orchestrator._wake`) es **datos frescos primero, luz después**, y es la **única navegación que sí espera a la red** (el resto pinta con caché y revalida por detrás, ver [Caché de lecturas](#caché-de-lecturas)): reserva el centinela de navegación (un doble toque no dispara dos despertados), deja la pantalla en "Hoy" -- lo que de paso saca de `STANDBY` --, **invalida toda la caché** (tras media hora suspendido no vale nada) y lee, bloqueando, lo que "Hoy" necesita. Como ese repintado ocurre con el brillo todavía a 0, el deck se enciende ya con el contenido correcto: sin destello de datos viejos ni doble repintado. A cambio, tarda lo que tarde la red (1-2 s). El `finally` que sube el brillo **no es decorativo**: si el proveedor está caído o falla el dispositivo, el deck tiene que encenderse igual o se quedaría negro para siempre.

### Qué se ve mientras está suspendido

El brillo de stand by **no es 0** a propósito: a 0 el deck parece apagado o colgado. `BRIGHTNESS_STANDBY = 10` (en `deck/session.py`) deja lo justo para que se distinga un icono, y es la constante a tocar para ajustarlo a ojo. Ojo: **el brillo del Stream Deck es global, no hay control por tecla**, así que ese valor ilumina tenuemente las 15 y subirlo se come parte del ahorro casi en proporción directa.

**Lo que se ve sale entero de `core.screens.STANDBY_LAYOUT`, y ese dict es el único sitio que hay que tocar para cambiarlo**:

```python
STANDBY_LAYOUT: dict[int, StandbyKey] = {
    7: StandbyKey("", "🌙"),   # tecla central: solo icono, sin texto
}
```

Las teclas que no aparecen se pintan negras. Añadir, quitar o mover contenido es editar entradas de ese dict — nada más del sistema cambia: `resolve_page` lo expande a las 15 teclas (rellenando con `_STANDBY_BLANK`) y `deck.renderer.render_standby_key` pinta cada una. Los colores y el tamaño de fuente están en `deck/style.py` (`COLOR_STANDBY`, `COLOR_TEXT_STANDBY`, `FONT_SIZE_STANDBY`). `StandbyKey` tiene `label` y `emoji`, igual que un botón de menú, así que una tecla puede llevar texto, icono o ambos.

Que se resuelva a las 15 teclas (y no solo a las que tienen contenido) es lo que hace que `render_page` la trate como un bloque, igual que el teclado numérico: si no, las teclas 0/5/10 recaerían en menú/paginación, que aquí no significan nada.

### Tres detalles que no son obvios y conviene no "simplificar"

- **Entrar en stand by pinta de verdad, y baja el brillo antes de pintar.** Pintar es necesario porque con brillo > 0 la pantalla anterior se seguiría intuyendo. Y el orden (brillo primero) hace que la transición se lea como un fundido en vez de como un parpadeo de pantalla nueva a plena luz.
- **`_on_auto_return_timeout` sale antes si está suspendido.** Con el botón "Suspender" el stand by se adelanta pero el temporizador de auto-retorno sigue armado; sin esa salida, a los 5 min sacaría de `STANDBY` sin encender la pantalla y dejaría el deck a oscuras con las teclas otra vez activas — justo lo que `"wake"` existe para impedir.
- **`_enter_standby` comprueba si ya está suspendido.** No es solo defensivo: pulsar "Suspender" reprograma el temporizador de stand by (`on_key_change` lo hace en toda pulsación), que volverá a disparar estando ya suspendido.

**Ninguna vista se "vacía": completar algo nunca lo saca de la lista.** Ver [Completar no hace desaparecer](#completar-no-hace-desaparecer) para el estándar completo. "Hoy" usa `_flat_page_builder` (no el mapeo estable de hábitos): `core.screens._today_items` construye, en cada resolución, la lista de **todos** los hábitos de hoy (hechos o no, ordenados por `(order, id)`) seguida de **todas** las tareas (pendientes o recién completadas, en el orden que ya trae el proveedor), y esa lista se reparte de cero desde la primera tecla disponible con `key_map.paginate` — sin reservar nada. Al completar un hábito o cerrar una tarea, `make_key_callback` repinta la **pantalla entera** (no solo esa tecla): la tecla en cuestión pasa a gris (`deck.renderer.render_habit`/`render_task`) en la misma posición, nada se recoloca. "Hábitos" hace lo mismo con su propio mecanismo (`_tiered_page_builder`, mapeo estable, ver [Reparto de teclas](#reparto-de-teclas)): muestra el estado de todos, hechos o no, para poder repasarlos.

**"Hoy" y "Hábitos" son las vistas que deshacen.** Como las dos enseñan los hábitos ya hechos (en gris), sirven para corregir una pulsación errónea: pulsar ahí un hábito **booleano** ya marcado hoy llama a `habit_undo` en vez de a `habit_step`, el checkin del día vuelve a 0 y la tecla se repinta en blanco (pendiente). Volver a pulsarla lo marca otra vez: el ciclo es reversible sin límite. Un hábito **cuantificable** no deshace nunca al pulsarlo — sigue sumando `step` aunque ya haya pasado el objetivo (`10/8` → `11/8`), que es justo lo que su tecla en gris significa. La decisión es pura y vive en `core/screens.py`: `ViewSpec.allows_undo` (`True` en "Hoy" y "Hábitos"; una vista nueva no lo hereda) más el tipo y el estado del hábito hacen que `resolve_press` devuelva una `PressAction` de tipo `"habit_undo"` en vez de `"habit"`. Una tarea nunca deshace por tap en ninguna vista (ver [Completar no hace desaparecer](#completar-no-hace-desaparecer): habits-core no tiene RPC para revertir un cierre).

**"Crear" es la única vista que escribe algo nuevo en vez de modificar lo que ya hay.** Lista las plantillas de `task_templates` marcadas con `show_in_deck` en la base — las tareas que se repiten **sin momento fijo** ("Cita peluquero"), que ni materializa `pg_cron` ni encadena `complete_task` —, y al pulsar una crea la ocurrencia con `instantiate_task`. La tarea nueva vence hoy (lo decide la base, el daemon no manda fecha) y aparece en "Hoy" y "Tareas" al instante.

Qué plantillas salen aquí **no se configura en el daemon**: es la columna `show_in_deck` de `../habits-core`, opt-in (`default false`). Añadir un botón nuevo es un `update`, no un despliegue.

Dos detalles que la distinguen de las demás:

- **La plantilla no desaparece al usarla**: se reutiliza. Lo que cambia es su color — y a diferencia de una tarea completada (gris hasta el siguiente refresco real, ver [Completar no hace desaparecer](#completar-no-hace-desaparecer)), una plantilla vuelve sola a su color normal en cuanto la ocurrencia que creó se cierra, sin esperar a ningún refresco.
- **`instantiate_task` no es idempotente** (dos pulsaciones, dos tareas), así que una plantilla que ya tiene una ocurrencia pendiente se pinta en **gris y su tecla no hace nada**. Es la única tecla de contenido del deck que se bloquea de verdad — en todo lo demás la regla es "la tecla nunca se bloquea, decide la base", pero aquí la base no puede decidir nada: no hay forma de distinguir un duplicado accidental de uno querido. Toda la lógica está en `core.screens._create_items`, que cruza las plantillas con `Task.template_id` y marca `Template.has_pending`; `resolve_press` lo convierte en `noop` y `render_template` en gris.

Ese cruce se **recalcula en cada resolución**, no se acumula: si la ocurrencia se cierra, la plantilla vuelve a estar disponible sola. Por eso `press_template`, al crear con éxito, inserta la tarea nueva en `tasks_ref` en vez de tocar `has_pending` a mano — marcar el flag se perdería en el primer repintado. Es tan reciente como el último ciclo: una ocurrencia creada desde otro cliente hace un minuto todavía no se ve, y se asume — el gris es una red, no un candado.

### Vista "Logs"

Lista los hábitos de solo registro (`purpose='log'` en `../habits-core`, vista `v_log_habits`, `HabitProvider.get_log_habits()`): a diferencia de "Hoy"/"Hábitos", un `LogHabit` **nunca** está "pendiente" ni "hecho" — es solo un botón para dejar constancia de que algo ocurrió hoy (p.ej. "Desperté"), y pulsarlo llama a `provider.step(habit)` exactamente igual que un hábito con objetivo (misma RPC `habit_step`, ver `orchestrator.press_habit`, que busca el id tanto en `habits_ref` como en `log_habits_ref` porque ambos comparten la misma acción `"habit"`).

**No tiene el eje pendiente/hecho de un hábito con objetivo** (no hay `goal` que comparar), pero sí tiene uno propio, derivado de `cumulative`: un log de registro único (`cumulative=False`, "Desperté") ya registrado hoy (`current_value > 0`) pasa al mismo gris `COLOR_HABIT_DONE`/`COLOR_TEXT_HABIT_DONE` que un hábito con objetivo hecho — misma señal, "ya llegaste, sigue pudiéndose pulsar" (`deck.renderer.render_habit`). Un log acumulable (`cumulative=True`, "Cocacola") **nunca** pasa a gris, tenga o no progreso hoy: cada pulsación es un registro más que se quiere seguir invitando a hacer, así que conserva siempre el `color` propio del hábito en la base (`"#RRGGBB"`, columna `habits.color`) — `deck.style.COLOR_HABIT_LOG_DEFAULT` si no tiene uno definido, con el texto en negro o blanco según cuál contraste más (`deck.renderer._contrasting_text_color`). Es el único fondo del deck que elige libremente el usuario en la base, así que es también el único que necesita ese cálculo en vez de una pareja de color fija a mano.

**Cada `LogHabit` es o bien un registro único diario, o bien acumulable — lo decide `habits.type` en la base, sin tocar código.** `type='Boolean'` (p.ej. "Desperté"): `habit_step` siempre fija el mismo valor (`h.goal`), así que pulsarlo varias veces el mismo día no deja más rastro que un solo registro; la tecla nunca enseña número, solo el nombre (`LogHabit.cumulative = False`), y pasa al gris de "hecho" (`COLOR_HABIT_DONE`, ver `deck.renderer.render_habit`) en cuanto se registra hoy — la única señal visual de que un log de registro único ya se pulsó. `type='Real'` (p.ej. "Cocacola"): `habit_step` **suma** `h.step` cada vez (mismo upsert `on conflict(habit_id, checkin_date)` que ya usa cualquier hábito cuantificable — es agnóstico de `purpose`, no hace falta ninguna RPC nueva para esto), y la tecla muestra el contador del día (`"Cocacola x3"`, o `"3 <unit>"` si el hábito tiene unidad) vía `LogHabit.display_label()`. Crear un log acumulable nuevo es solo un dato: `insert into habits (purpose, type, ...) values ('log', 'Real', ...)` — sin migración ni tocar este repo.

Como "Hoy"/"Tareas"/"Crear", pagina de cero cada ciclo (`core.screens._flat_page_builder`, sin el mapeo persistido de "Hábitos" — ver [Reparto de teclas](#reparto-de-teclas)), ordenados por `(order, id)`. Un log no tiene `is_done` que filtrar (nunca está "pendiente" ni "hecho"), así que en la práctica cada log mantiene la misma tecla mientras no cambien los logs que hay, sin necesitar la persistencia de `core.key_map`.

### Secciones

Las secciones de hábitos (`habit_sections`/`habits.section_id` en `../habits-core`) tienen **un único punto de entrada por defecto**: la tecla 1 de "Hábitos" (`core.screens.KEY_HABITS_SECTIONS_SHORTCUT`), que abre "Secciones" (`core.screens.ScreenKind.SECTIONS_MENU`) — una lista **dinámica y paginada** de todas las secciones que tengan algún hábito hoy, construida por `core.screens._section_menu_entries` a partir de `Habit.section_name` en cada resolución. Añadir una sección es **puro dato**: `update habits set section_id = ... where ...` en `../habits-core`, sin tocar ni desplegar este repo — la sección aparece sola en "Secciones" en cuanto algún hábito la tenga asignada y toque hoy. El menú principal no tiene entradas de sección por defecto (a propósito, para no duplicar el camino), **salvo las que el propio usuario fije desde el deck** — ver más abajo.

Entrar en una sección desde esa lista tiene **exactamente el mismo comportamiento** que "Hábitos": se ven todos los hábitos con objetivo de esa sección, hechos hoy en gris o pendientes en blanco, y pulsar un booleano ya hecho lo **deshace** (`core.screens._undoes` siempre deja deshacer cuando `ScreenState.section_name` no está vacío, sin necesitar una entrada en `VIEWS`).

La tecla 1 de "Hábitos" está reservada de forma permanente para este atajo, mismo criterio que `KEY_TIMER_SHORTCUT` (tecla 7) en el menú: ningún hábito la ocupa nunca, ni en la página 0 (`core.key_map.update_mapping` la excluye del reparto, y libera/reasigna a otra tecla el hábito que la ocupara antes de esta reserva) ni en el sobrante de páginas siguientes (`core.screens._place_items` también la excluye ahí). El botón en sí solo se pinta en la página 0 (`core.screens.resolve_page`), igual que el atajo de cronómetro.

`section_name` es un campo de `provider.base.Habit` (no solo de `BooleanHabit`/`RealHabit`, para que se pueda leer sin `isinstance`, igual que `manual_entry`) que llega ya resuelto por la base: `v_today_habits` en `../habits-core` hace `left join habit_sections` y expone `section_name` (el nombre, no el UUID crudo de `section_id`) — así el cliente no tiene que resolverlo por su cuenta. `LogHabit` no lo tiene: una sección, como "Hábitos", solo trabaja con hábitos con objetivo.

**Una sección no es una vista de `VIEWS` ni un `ScreenKind` propio**: es un campo más de una pantalla `ScreenKind.VIEW` (`ScreenState.section_name`), resuelto por `core.screens._section_page` en vez de por `VIEWS[view_id]` — `view_id` queda sin consultar mientras `section_name` no esté vacío. La razón de este diseño (y no un `ScreenKind.SECTION` nuevo) es que **entrar en `ITEM_OPTIONS`/`NUMERIC_ENTRY` no toca `view_id`/`page`** (ver [Menú y pantallas](#menú-y-pantallas)), así que reutilizar el mismo mecanismo para `section_name` hace que mantener pulsado un hábito de una sección y pulsar "Volver" regresen solos a esa misma sección, sin ningún campo ni caso especial nuevo. `orchestrator._enter_view` limpia `section_name` al entrar en cualquier vista de `VIEWS` (si no, quedaría un filtro viejo puesto por error); `orchestrator._enter_section` es su equivalente para entrar en una sección (mismo patrón: pintar con caché + `_revalidate_screen()`, que ahí solo puede pedir hábitos).

Como "Logs"/"Cronómetros": ningún hábito desaparece de una sección solo por completarse (queda en gris, no se filtra), así que paginar de cero cada vez (`paginate` + `_place_items`, sin pasar por el mapeo persistido de `core.key_map`) ya da tecla estable entre ciclos sin necesitar esa persistencia.

**Fijar una sección como botón directo del menú principal**: mantener pulsada una entrada de sección (mismo mecanismo de mantener-pulsado que un hábito/tarea, ver [Menú de opciones de un hábito/tarea](#menú-de-opciones-de-un-hábitotarea-mantener-pulsado)) abre `core.screens.ScreenKind.SECTION_OPTIONS`, con una única tecla (14): "Fijar en menú" (verde) si la sección no está fijada, "Quitar del menú" (ámbar) si ya lo está — alterna `core.pinned_sections` y se queda en la misma pantalla para poder alternar varias veces seguidas. Esto funciona **desde las dos pantallas** donde puede aparecer un botón de sección: dentro de "Secciones" (mantener pulsada una entrada de la lista) y también sobre un botón ya fijado **en el propio menú principal** — mantenerlo pulsado ahí abre igualmente las opciones de esa sección en concreto, en vez de entrar en ella. "Volver" (tecla 0) regresa a la pantalla exacta desde la que se abrió (`ScreenState.entry_section_origin`, ver más abajo), en la misma página en la que estabas (no toca `screen.page` al entrar). Ninguna entrada de "Secciones" ni del menú principal cambia de icono al fijarse: una sección no tiene icono propio en `../habits-core`, y forzar uno genérico (p.ej. "📌") en todas las fijadas las volvería indistinguibles entre sí con más de una a la vez — se muestran solo con su nombre, como siempre.

Es **una preferencia local del deck, no un dato de `../habits-core`**: vive en `core/pinned_sections.py` (`load()`/`toggle()`, mismo patrón `load_map()`/`save_map()` que `core/key_map.py` con `habit_key_map.json`), persistida en `pinned_sections.json` (`config.PINNED_SECTIONS_FILE`) junto a `habit_key_map.json`. No pasa por ningún `ProviderError` ni `_claim`/`_release`: es una escritura a fichero local, no una llamada a Supabase, así que `orchestrator._toggle_section_pin` la ejecuta directo desde `_dispatch_navigation`, sin el manejo de fallos de red del resto de acciones. Cada sección fijada aparece en el menú principal como un botón más (`core.screens._pinned_section_menu_entries`, concatenado a `MENU_ENTRIES` en la rama `ScreenKind.MENU` de `resolve_page`) que resuelve al mismo `PressAction("enter_section", ...)` que cualquier otro camino a una sección — con el mismo comportamiento de siempre al entrar (deshacer incluido). Una sección fijada que se queda sin hábitos hoy simplemente no aparece ese día (mismo criterio que "Secciones"), sin necesidad de despinnearla a mano.

`ScreenKind.SECTION_OPTIONS` es una pantalla propia, no una reutilización de `ScreenKind.ITEM_OPTIONS`: su "Volver" tiene que regresar a la pantalla desde la que se abrió (`ScreenState.entry_section_origin`), no siempre a `ScreenKind.VIEW` (que es a donde siempre vuelve `ITEM_OPTIONS`), así que necesita sus propios campos (`ScreenState.entry_section_name`/`entry_section_origin`) y su propia pareja `orchestrator._enter_section_options`/`_exit_section_options`. Sí reutiliza el pintado genérico de `ResolvedPage.key_options`/`deck.renderer.render_option_entry` (con el `kind` nuevo `"toggle_pin"`), así que no hizo falta tocar `deck.renderer.render_page`.

Mantener pulsado un botón de sección arma el mismo temporizador en las dos pantallas donde puede aparecer (`core.screens.PressAction("enter_section", ...)` en ambas) y, al disparar, **las dos abren lo mismo**: `ScreenKind.SECTION_OPTIONS` para esa sección en concreto (`enter_section_options`). La diferencia es solo el destino de "Volver": `orchestrator.on_key_change` captura la pantalla de origen (`screen_kind`, en el momento de la pulsación) y se guarda en `entry_section_origin`, así que "Volver" desde "Secciones" regresa a "Secciones" y "Volver" desde un botón fijado en el menú principal regresa al menú principal — nunca se mezclan entre sí.

### Proyectos

Mismo mecanismo que [Secciones](#secciones), letra por letra, pero para `projects`/`tasks.project_id` en `../habits-core` y sobre "Tareas" en vez de "Hábitos": tecla 1 de "Tareas" (`core.screens.KEY_TASKS_PROJECTS_SHORTCUT`) abre "Proyectos" (`ScreenKind.PROJECTS_MENU`, `core.screens._project_menu_entries`, derivado de `Task.project_name`); entrar en un proyecto es exactamente "Tareas" pero filtrada (`core.screens._project_page`, `ScreenState.project_name`), sin deshacer porque una tarea nunca lo tiene; mantener pulsado un proyecto (desde "Proyectos" o desde un botón ya fijado en el menú principal) abre `ScreenKind.PROJECT_OPTIONS` con el mismo botón único "Fijar en menú"/"Quitar del menú" (`core.pinned_projects`, `pinned_projects.json`, `orchestrator._toggle_project_pin`) — misma ausencia deliberada de icono al fijar, mismo `ScreenState.entry_project_origin` para que "Volver" regrese a la pantalla exacta de origen.

**Única diferencia real con Secciones**: `project_name` no salía de fábrica resuelto en `v_today_tasks` (a diferencia de `section_name`, que ya lo estaba en `v_today_habits` antes de "Secciones dinámicas") — hizo falta una migration en `../habits-core` (`left join projects`, mismo patrón que la de `section_name`) para exponerlo, así que añadir "Proyectos" sí tocó el otro repositorio, siguiendo su proceso develop→test→main (ver `../habits-core/CLAUDE.md`).

Un proyecto filtrado sí marca `Task.timer_running`/`total_seconds` igual que "Tareas" (`core.screens._project_page` llama a `_mark_running_task` explícitamente, al no pasar por ningún `PageBuilder`), así que el marco/prefijo de cronómetro se ve igual ahí que en "Tareas" sin filtrar.

### Vista "Cronómetros"

Cronómetros tipo Toggl Track, aparte de hábitos y tareas: botones que llevan la cuenta de en qué se invierte el tiempo, asociados a una tarea concreta (desde su menú de opciones, ver arriba) o a una **etiqueta rápida** predefinida en `../habits-core` (`timer_labels`, vista `v_timer_labels`, `TimerProvider.get_timer_labels()`) — mismo patrón que `task_templates.show_in_deck` para "Crear": `timer_labels.show_in_deck` opt-in, se crean/archivan a mano por SQL, no hay cliente que las gestione todavía. Cada etiqueta es **una sola tecla que alterna** (parada → pulsar → arranca; corriendo → pulsar la misma tecla → para), nunca dos botones separados de iniciar/parar.

**Como mucho un cronómetro corriendo a la vez, tipo Toggl**: arrancar uno nuevo para automáticamente el que estuviera corriendo. Esto lo decide `rpc/timer_toggle` en la base mirando el estado **real**, nunca lo que el deck cree — con `REFRESH_SECONDS = 900` (15 min) el deck puede llevar un rato sin refrescar, y al ser una sola tecla para las dos direcciones equivocarse de sentido no es solo cosmético (a diferencia de `habit_step`, que siempre suma). Por eso `orchestrator.press_timer_toggle` **nunca hace mutación optimista**: tras un toggle exitoso siempre relee de verdad el estado de los cronómetros (`refresh_after_write(TIMER_RESOURCES)`), igual que `press_habit_undo_option` con los hábitos.

Es un **cuarto tipo de ítem pintable** en `core/screens.py`, no solo una vista más registrada en `VIEWS`: `ViewItem`/`_place_items`/`PageBuilder`/`ItemsFn`/`ResolvedPage` — antes cerrados a `Habit`/`Task`/`Template` — ganan `TimerLabel`/`key_timer`. Cualquier vista nueva que solo mezcle los tres tipos ya existentes no necesita este trabajo extra; una que añada un tipo de ítem pintable nuevo, sí.

`core.screens._timer_items` cruza las etiquetas con `RunningTimer` (`get_running_timer()`, 0 o 1 fila garantizado por la base) para marcar `TimerLabel.running`/`started_at` antes de repartirlas — mismo patrón que `_create_items` marcando `Template.has_pending` — y con `daily_totals` (`get_daily_totals()`, vista `v_timer_daily_totals` en `../habits-core`: segundos acumulados **hoy** por id de tarea/etiqueta, sumando todos sus bloques del día) para marcar `TimerLabel.today_seconds`. Corriendo, `deck.renderer.render_timer` pinta `COLOR_TIMER_RUNNING` (rosa) con el nombre arriba y el tiempo transcurrido debajo entre corchetes (p.ej. `"Lectura\n[00:05]"`), sin emoji — con dos líneas no hace falta recordar cuál está activo, se lee en la propia tecla; parada, `COLOR_TIMER_STOPPED` (turquesa) con `deck.renderer._stopped_timer_label` (el nombre solo si `today_seconds` es 0, o `"[total] nombre"` si ya acumuló algo hoy, p.ej. `"[00:25] Lectura"`) + emoji de siempre. El tiempo/total se recalcula en cada repintado (`_format_elapsed`/`_format_duration`, único cálculo de tiempo del lado cliente en todo el proyecto, limitado a presentación) — nunca un contador que incrementa solo. La misma opción existe en el menú de una tarea (tecla 2 de `TASK_OPTIONS_LAYOUT`, ver [Menú de opciones de un hábito/tarea](#menú-de-opciones-de-un-hábitotarea-mantener-pulsado)): ahí también se pinta, corriendo, el título de la tarea (`running_timer.title`, ya denormalizado — no hace falta cruzar con `Task`) y el tiempo debajo entre corchetes, en vez del texto "Detener cronómetro" y su icono de cuadrado ⏹️, cuando esa tarea es la que está corriendo (esa opción concreta **no** muestra el total del día, solo la vista "Cronómetros" y el atajo de la tecla 7).

**Una tarea con su cronómetro corriendo se marca también en "Hoy"/"Tareas"**: `core.screens._mark_running_task` cruza las tareas contra `running_timer`/`task_totals` (mutando `Task.timer_running`/`total_seconds`, mismo patrón) y `deck.renderer.render_task` superpone un marco de aviso (`COLOR_TASK_TIMER_BORDER`, el mismo rosa de "corriendo") sobre el color de prioridad de siempre — salvo en prioridad alta, un rojo ya sólido, donde ese marco rosa se fundiría con el fondo: ahí se usa blanco (`COLOR_TASK_TIMER_BORDER_HIGH_PRIORITY`). Solo un marco, no un color nuevo: la prioridad sigue siendo la que decide el fondo.

**La misma tecla de tarea antepone el acumulado de SIEMPRE, no el de hoy**: `task.total_seconds` sale de `get_task_totals()` (vista `v_task_timer_totals`, sin filtrar por día — al revés que `daily_totals`), y si es mayor que 0, `deck.renderer._time_prefixed_label` antepone `"[total] "` al título (p.ej. `"[00:25] Escribir informe"`); si nunca se cronometró esta tarea (`total_seconds == 0`), la tecla se pinta igual que siempre, solo el título. Una tarea es una ocurrencia concreta, no un cajón recurrente entre días como una etiqueta — por eso aquí importa el acumulado de toda su vida, no el de hoy (que sí tiene sentido para una etiqueta, ver arriba). Este total es independiente del marco de "corriendo": pueden darse los cuatro casos (sin marco/sin total, sin marco/con total, con marco/sin total recién arrancado, con marco/con total).

**El tiempo transcurrido no se actualiza solo entre pulsaciones**: una tecla del deck es una imagen estática, no hay nada "vivo". Sin ayuda, se quedaría congelado en el valor que tenía la última vez que se repintó la pantalla (al pulsar algo, o cada `REFRESH_SECONDS` = 15 min) — con un cronómetro recién arrancado, eso se ve como "siempre 00:01". Por eso hay **dos** temporizadores aparte en `orchestrator.main()`, independientes de `auto_return_timer`/`standby_timer` (no se reprograman con la actividad del usuario) y que solo corren mientras `running_timer_ref["value"]` no sea `None` (y el deck no esté en stand by):

- `_timer_tick` (`config.TIMER_TICK_SECONDS`, 1s) repinta la pantalla activa **sin refetch** — recalcula el tiempo en el cliente a partir del `started_at` ya cacheado —, así que si estás mirando "Cronómetros" o el menú de opciones de una tarea con su cronómetro corriendo, el tiempo sube solo cada segundo.
- `_timer_sync` (`config.TIMER_SYNC_SECONDS`, 60s) relee de verdad **solo las tres lecturas de cronómetro** (`core.cache.TIMER_RESOURCES`: cuál corre y los dos acumulados) y repinta para corregir esa cuenta local — deriva de reloj, o que otro cliente haya parado/arrancado el cronómetro entre medias — sin esperar a los 15 min de `REFRESH_SECONDS`.

Como "Logs": pagina de cero cada ciclo (`core.screens._flat_page_builder`), ordenadas por `(order, id)`; ninguna etiqueta desaparece de la lista salvo que se archive, así que en la práctica cada una mantiene la misma tecla sin necesitar `core.key_map`. No entra en `_HOLD_KINDS`: pulsar una etiqueta actúa al instante, sin distinguir toque corto/largo (como una tecla de "Crear").

### Vista "TickTick"

**PoC deliberadamente independiente de `habits-core`**: lista las tareas pendientes de una cuenta de [TickTick](https://ticktick.com) (API abierta oficial, `open/v1`) via `ticktick/client.py::TickTickApiProvider`, sin ninguna migración, RPC ni escritura cruzada con la base de `../habits-core`. Es un origen de datos aparte, no una vista más de `VIEWS`.

**Por qué vive fuera de `VIEWS`/`PageBuilder`**: ese mecanismo reparte 8 conjuntos de datos de habits-core a todas las vistas porque necesitan cruzarse entre sí (ver más arriba). TickTick no cruza con nada de eso, y sobre todo su refresco **tiene que ir desacoplado** del ciclo de habits-core — colarlo como una vista más forzaría threading un 9º parámetro por las firmas de las 6 vistas existentes sin necesidad real, y acoplaría su cadencia a `refresh_cycle()`. En su lugar es una **pantalla especial** más, al mismo nivel que `ScreenKind.NUMERIC_ENTRY`/`ITEM_OPTIONS`/`STANDBY`: `ScreenKind.TICKTICK`, resuelta por su propia rama en `core.screens.resolve_page` (`ResolvedPage.key_ticktick`). La tecla 5/10 se comporta **normal** (paginación); la 0 solo se reinterpreta filtrada a un proyecto (ver justo abajo) — en la principal sigue abriendo el menú de siempre.

**Pantalla principal: proyectos primero, luego las tareas sueltas**: al entrar en "TickTick" (`ScreenState.ticktick_project_id` vacío), la pantalla mezcla en una sola lista paginada un botón por cada proyecto de TickTick (azul de navegación, `MenuEntry` con `action="enter_ticktick_project"` — mismo mecanismo y pintado que un botón de "Secciones"/"Proyectos") seguido de las tareas sin proyecto reconocido: las del Inbox y, si las hay, las de un proyecto archivado (`closed`, sin botón propio — ver más abajo). Los proyectos van siempre primero y ordenados como en la propia TickTick (`sortOrder`). Pulsar un botón de proyecto filtra esa misma pantalla a sus tareas (`ScreenState.ticktick_project_id` puesto, mismo patrón que `section_name`/`project_name` de una vista — un campo más de la pantalla, no un `ScreenKind` propio); entrar en "TickTick" desde el menú siempre limpia el filtro (`orchestrator._enter_ticktick`).

**Filtrada a un proyecto, la tecla 0 es "Volver" a la principal**, no el menú: resuelve a `PressAction("exit_ticktick_project")` (`orchestrator._exit_ticktick_project`, sin red — solo limpia `ticktick_project_id` y repinta), reutilizando el mismo botón azul (`OptionEntry`/`render_option_entry`, `_ITEM_OPTIONS_BACK`) que "Volver" en el menú de opciones de un hábito/tarea. Único sitio de la pantalla "TickTick" donde la tecla 0 no abre el menú principal — mismo criterio de excepción que ya usan `ITEM_OPTIONS`/`SECTION_OPTIONS`/`PROJECT_OPTIONS`.

**Tap para completar, tap sobre una gris para reabrir**: pulsar una tarea pendiente (color por prioridad, igual escala 0/1/3/5 que `provider.base.Task` — coincidencia del propio contrato de TickTick) la completa y la pinta en el mismo gris `COLOR_HABIT_DONE` que un hábito hecho; pulsarla de nuevo la reabre (por si fue un error) y vuelve a su color. Una sola acción para las dos direcciones (`PressAction("ticktick_toggle", task_id)`, mismo criterio que `timer_toggle`): quien la ejecuta (`orchestrator.press_ticktick_toggle`) relee `TickTickTask.completed` en ese momento para decidir `complete_task`/`uncomplete_task`, en vez de que lo decida `resolve_press` contra una página que podría haberse quedado desfasada.

`uncomplete_task` **no está documentado** en la API oficial de TickTick (solo existe `POST .../task/{id}/complete`): se validó a mano contra la API real antes de implementarlo — `POST /open/v1/task/{taskId}` (Update Task) con el cuerpo mínimo `{"id", "projectId", "status": 0}` reabre la tarea sin tocar ningún otro campo (no es un reemplazo completo). Si en algún momento TickTick cambia ese comportamiento y deja de funcionar, la opción es recortar `TickTickProvider` a solo `complete_task` y aceptar que una tarea completada por error solo se puede corregir en la propia app de TickTick.

Mismo estándar que una tarea de habits-core (ver [Completar no hace desaparecer](#completar-no-hace-desaparecer)): `orchestrator.press_ticktick_toggle` muta el objeto en `ticktick_tasks_ref` de forma optimista, sin sacarlo de la lista — `TickTickTask.completed` es un estado visible que se queda pintado. Solo el **próximo refresco real** desde la API (`orchestrator.ticktick_refresh_cycle`) deja de traerla — `POST /task/filter` con `status: [0]` ya filtra a solo tareas sin completar — y entonces desaparece de la pantalla de verdad. **A diferencia de una tarea de habits-core**, aquí sí hay undo real (`uncomplete_task`, ver arriba): es el único de los tres casos del estándar donde pulsar el elemento ya gris revierte el check en vez de no hacer nada.

**Refresco propio, nunca compartido con habits-core**: `orchestrator.ticktick_refresh_cycle()` es hermana de `refresh_cycle()`, no una llamada más dentro de ella — nunca toca `mapping` ni ningún `*_ref` de habits-core, ni al revés. Trae tareas (`get_tasks()`) y proyectos (`get_projects()`, para los botones de la pantalla principal) en la misma pasada, bajo un único código de error para las dos. Se dispara al entrar en la pantalla principal (`orchestrator._enter_ticktick`, mismo criterio que `_enter_view`: pinta con lo cacheado y solo relee si esos datos tienen ya más de `CACHE_TTL_SECONDS`, ver [Caché de lecturas](#caché-de-lecturas)) y, mientras "TickTick" siga siendo la pantalla activa (en cualquiera de sus dos variantes, principal o filtrada por proyecto), también en el ciclo periódico de `REFRESH_SECONDS` del bucle principal (`orchestrator._is_ticktick_active`) — **nunca** si no se está mirando, para no gastar peticiones a la API de TickTick sin necesidad. Entrar en un proyecto desde la pantalla principal (`orchestrator._enter_ticktick_project`) **no** dispara este refresco: filtra localmente las tareas que ya trajo `get_tasks()` (todas, de cualquier proyecto), así que navegar entre proyectos es instantáneo.

**`get_tasks()` trae todas las tareas pendientes de golpe, Inbox incluido, en una única petición** (`ticktick/client.py::TickTickApiProvider.get_tasks`, documentada en `../ticktick.http`): `POST /task/filter` con `{"status": [0]}` y sin `projectIds` devuelve de una sola vez las pendientes de todos los proyectos **y del Inbox** — el Inbox no tiene entrada en `GET /project` (no es un "proyecto" para ese endpoint), pero sí tiene un `projectId` interno no documentado (`"inbox" + id de usuario`) que funciona igual que cualquier otro tanto para leer como para completar/reabrir. No distingue proyectos `closed`: una tarea pendiente en un proyecto archivado se sigue trayendo igual, y como ese proyecto no tiene botón en la pantalla principal (ver `get_projects` abajo), esa tarea se ve ahí junto a las del Inbox. `get_projects()` trae todos los proyectos (`GET /project`, incluidos los `closed`) para los botones de la pantalla principal — filtrar los cerrados es cosa de `core.screens.resolve_page`, no de este adaptador. `get_project_tasks` (tareas de UN proyecto vía `GET /project/{id}/data`) se mantiene sin usar por nada hoy: entrar en un proyecto filtra localmente lo que ya trajo `get_tasks()` en vez de pedirlo aparte (ver arriba).

**Sin token configurado** (`TICKTICK_ACCESS_TOKEN` ausente del `.env`, ver [Disposición en la Pi](#disposición-en-la-pi)): `ticktick_provider` queda en `None` en `main()` **sin tumbar el daemon** (a diferencia de `SupabaseProvider()`, que sí hace `sys.exit(1)`) — es una capacidad añadida, no el núcleo del deck. La pantalla "TickTick" pinta directamente el código `AUTH` en todas sus teclas sin intentar red.

**Sin flujo OAuth2 con navegador**: la doc oficial de TickTick (`ticktick-doc.txt`) lo exige (`authorize` → `code` → canjear por `access_token`), pero la Pi no tiene navegador. Esta PoC asume que el `access_token` ya se obtuvo fuera del deck (Developer Center de TickTick) y se pega directamente en el `.env`; sin refresh token documentado, cuando caduque hay que regenerarlo a mano y reiniciar el servicio, mismo procedimiento operativo que `SUPABASE_ACCESS_TOKEN`.

## Caché de lecturas

Los datos de la base viven en memoria del daemon (`orchestrator.main` → `habits_ref`, `tasks_ref`…), y `core/cache.py` es lo que dice **cuándo hay que volver a pedirlos**. Nada de esto toca la lógica de negocio: una escritura sigue yendo directa a su RPC y la base sigue decidiendo el resultado; esto solo evita releer lo que ya se sabe.

**El problema que resuelve.** Antes, entrar en cualquier vista disparaba un refresco completo — las **ocho** lecturas, siempre, en el hilo de callbacks del deck — aunque los datos tuvieran dos segundos y aunque esa vista pintara solo una de ellas. El patrón "Hábitos → menú → Hábitos" pedía los mismos hábitos dos veces en cinco segundos, más tareas, plantillas, cronómetros y totales que esa pantalla ni enseña; y mientras duraba, ninguna tecla respondía.

Tres piezas:

- **Una lectura = un `Resource`** (`core/cache.py`): `HABITS`, `LOG_HABITS`, `TASKS`, `TEMPLATES`, `TIMER_LABELS`, `RUNNING_TIMER`, `DAILY_TOTALS`, `TASK_TOTALS` (los ocho del contrato de `habits-core`, agrupados en `SUPABASE_RESOURCES`) y `TICKTICK` (la PoC aparte, ver [Vista "TickTick"](#vista-ticktick)). Cada pantalla declara cuáles necesita: una vista en su `ViewSpec.needs`, el resto en `core.screens.needs_for`. "Hábitos" pide hábitos y **nada más**; "Logs", solo los logs.
- **TTL** (`config.CACHE_TTL_SECONDS`, 60 s): una lectura con menos de un minuto se da por buena y no se repite. Es lo que hace que ir y volver entre pantallas no cueste ni una petición.
- **Generación + single-flight** (`ResourceCache.begin_fetch`/`end_fetch`/`invalidate`): lo que mantiene la sincronía con la base. Ver "Qué garantiza" más abajo.

**Al entrar en una pantalla: pintar ya, refrescar detrás** (stale-while-revalidate). `orchestrator._enter_view` (y `_enter_section`/`_enter_project`/`_enter_menu`/`_enter_ticktick`) pinta con lo cacheado dentro de `screen_lock` y luego llama a `_revalidate_screen()`, que pide **solo lo que esa pantalla necesita y esté caducado**, en el hilo de refresco (`_revalidate_async`, un `ThreadPoolExecutor` de un hilo). Cuando la respuesta llega, se aplica y se repinta. Consecuencias que conviene tener claras:

- La navegación **nunca** espera a la red, ni siquiera cuando sí hay que releer. El hilo de callbacks del deck queda libre: pulsar otra tecla durante una relectura funciona.
- Si los datos estaban caducados, esa pantalla **se pinta dos veces** (caché al instante, datos frescos ~1 s después). Es el precio de no esperar.
- Un cambio hecho desde otro cliente (la PWA) en el último minuto no se ve hasta que caduca el TTL. Se ajusta con `CACHE_TTL_SECONDS`, que es la única palanca.

**Excepciones deliberadas:**

- **"Crear"** declara `max_age_seconds = 0`: relee las tareas siempre al entrar, porque de ellas sale el gris que impide crear una ocurrencia duplicada (`instantiate_task` no es idempotente, ver [Menú y pantallas](#menú-y-pantallas)).
- **Despertar del stand by** (`orchestrator._wake`) es la **única navegación que sí espera a la red**: invalida todo (el deck lleva media hora o más suspendido, lo cacheado no vale) y lee "Hoy" bloqueando, con el brillo todavía a 0, para encender ya con el contenido correcto. Ver [Stand by](#stand-by).

**Tras una escritura**, cada `press_*` avisa de lo que ha podido cambiar, y hay dos niveles:

| | Qué hace | Quién la usa |
|---|---|---|
| `invalidate(...)` | Marca caducado, **sin pedir nada ahora** | Escrituras cuyo resultado optimista ya es exacto: paso de hábito, entrada manual, completar/omitir una tarea, crear desde plantilla, toggle de TickTick |
| `refresh_after_write(...)` | Marca caducado **y relee ya**, por detrás | Escrituras cuyo optimista no basta: deshacer y ajustar un hábito (el valor fiable es el de la base, y en `weekly_quota` es el contador semanal), cambiar la prioridad (reordena la lista), cualquier toggle de cronómetro (la base pudo parar otro distinto del pulsado) |

Los conjuntos están en `core/cache.py`: `HABIT_RESOURCES` (los dos tipos de hábito juntos, porque un hábito pulsado puede venir de cualquiera de las dos lecturas), `TIMER_RESOURCES` (cuál corre + los dos acumulados) y `TASK_WRITE_RESOURCES` (tareas + cronómetros: `complete_task`/`skip_task` paran en la base cualquier cronómetro abierto de esa tarea, en el mismo commit).

**Qué garantiza (y por qué no se pierde sincronía):**

- Las escrituras **nunca** se cachean ni se encolan: van directas a su RPC y usan su respuesta. La caché es solo de lecturas.
- **Una lectura que empezó antes de una escritura nunca se aplica.** `invalidate` sube la generación del recurso; cuando esa lectura vuelve, `end_fetch` ve que la generación cambió, **descarta** el resultado y `_fetch_resources` lo vuelve a pedir. Sin esto, una lectura de tareas lanzada justo antes de cerrar una tarea devolvería esa tarea a la pantalla, deshaciendo visualmente lo que acabas de hacer.
- **Nunca se piden dos veces los mismos datos a la vez**: si ya hay una lectura en vuelo, `begin_fetch` devuelve `None` y la que ya corre repinta por las dos (un doble toque en el menú no dispara dos peticiones; por eso `_enter_view` ya no necesita el centinela `_claim`, que ahora solo usa `_wake`).
- **Una lectura fallida no se da por fresca**: guarda su código (que se pinta en tecla como siempre) y queda caducada, así que se reintenta en la siguiente navegación en vez de esperar al ciclo de 15 min.
- Lo pintado y lo que hace cada tecla **siguen sin poder desincronizarse**: ambos salen del mismo `resolve_page` bajo el mismo `screen_lock`, y aplicar datos + repintar + re-registrar el callback sigue ocurriendo junto, en `_paint_current_screen`.

**Cómo verlo en el journal.** Cada lectura real imprime una línea: `Lectura [habits] red 180 ms, pintado 310 ms`. Su **ausencia** es la otra mitad de la información: navegar sin que aparezca ninguna línea significa que la caché sirvió los datos y no se tocó la red.

**Transporte.** Aparte de la caché, `provider/supabase.py` reutiliza una única `requests.Session` (`_build_session`) para todas las peticiones: keep-alive, así que dejan de pagar un handshake TLS cada una — en la Pi eso pesaba más que los datos. Solo reintenta fallos de **conexión** (`connect=1`, `read=0`), que son los que garantizan que la petición no llegó a enviarse: seguro también para `instantiate_task`, que no es idempotente.

## El bucle principal

`main()` construye el proveedor (`sys.exit(1)` si falla), abre la sesión del deck, carga el mapeo y entra en un bucle infinito de `refresh_cycle()` separados por `time.sleep(REFRESH_SECONDS)` (900s). Ese ciclo periódico relee **todo** lo de `habits-core` y es la red de seguridad de la caché: lo que no se haya refrescado por navegar o por escribir (ver [Caché de lecturas](#caché-de-lecturas)) cae aquí de todas formas. El bucle también dispara `orchestrator.ticktick_refresh_cycle()`, pero solo mientras la pantalla "TickTick" sea la activa (ver [Vista "TickTick"](#vista-ticktick)) — es una lectura completamente aparte, con su propio proveedor (`ticktick_provider`, que puede ser `None` sin tumbar el daemon) y sus propios datos, nunca mezclada con las de habits-core. **En stand by el ciclo se salta entero** (`if not _is_standby()`): no tiene sentido pedir datos ni repintar una pantalla apagada, y el despertado ya fuerza su propia lectura completa. El bucle sigue despertando cada 15 min sin hacer nada; no compensa complicarlo. El mismo `SupabaseProvider` se usa por sus cuatro puertos (`habit_provider` / `task_provider` / `template_provider` / `timer_provider`), solo para dejar explícito qué capacidad usa cada llamada. Todo el estado de pantalla (`screen: core.screens.ScreenState`, `mapping`) está serializado por un `screen_lock` que comparten las lecturas, las funciones de navegación y el callback de tecla (incluido `repaint()` tras un paso/cierre con éxito), para que un refresco y una pulsación del usuario nunca se entrelacen.

**Todas las lecturas pasan por `orchestrator._fetch_resources(resources)`**, que sustituyó a los ocho bloques `try/except` copiados que tenía el `refresh_cycle` antiguo: ahora el llamador dice **qué** quiere y una tabla (`fetchers`, `fetch_labels`, `fetch_order`, `_apply`) hace el resto. Quién pide qué:

| Quién | Qué pide |
|---|---|
| Bucle periódico (`refresh_cycle`, cada `REFRESH_SECONDS`) | `SUPABASE_RESOURCES` (las 8) |
| Entrar en una pantalla (`_revalidate_screen`) | Lo que esa pantalla necesite **y esté caducado** |
| Una escritura (`invalidate`/`_refresh_after_write`) | Lo que esa escritura haya podido cambiar |
| `_timer_sync` (cada `TIMER_SYNC_SECONDS`, con un cronómetro corriendo) | `TIMER_RESOURCES` (3) |
| Despertar del stand by (`_wake`) | Lo que necesite "Hoy", **bloqueando**, tras invalidarlo todo |
| Bucle periódico, solo con "TickTick" abierta (`ticktick_refresh_cycle`) | `Resource.TICKTICK` |

**Las lecturas de red se hacen SIN sujetar `screen_lock`** — solo aplicar sus resultados y repintar, al final, lo hace. No siempre fue así: hasta que se detectó en producción, las ocho corrían bajo el lock, y `on_key_change` necesita ese mismo lock para resolver cualquier pulsación — con una petición hasta 10s de timeout (`provider/supabase.py`) y `TIMER_SYNC_SECONDS` (60s) disparando el ciclo completo cada minuto mientras un cronómetro seguía corriendo, una red lenta dejaba el deck entero sin responder durante ese rato, cada minuto. Se descubrió con un timeout real de 10s en `get_daily_totals` y un fallo de DNS en `get_log_habits` en el mismo arranque. Hoy hay **dos** defensas contra eso, y conviene no quitar ninguna: la red va fuera del lock, y además la dispara `_revalidate_async` en su propio hilo (`ThreadPoolExecutor` de uno), así que el hilo de callbacks del deck ni siquiera espera a que termine.

Cada lectura, en `_fetch_resources`:

1. **Se reserva** con `cache.begin_fetch`. Si ya hay una igual en vuelo, se salta (esa repinta por las dos).
2. **Se pide**, fuera del lock, en su propio `try/except ProviderError`: la que falla guarda su código corto (`AUTH`/`NET`/`API`) y **no** toca los datos, que se conservan del ciclo anterior. Una lectura fallida no afecta a las demás ni se da por fresca.
3. **Se cierra** con `cache.end_fetch`, ya bajo `screen_lock`. Si entre medias hubo una escritura sobre eso, el resultado se **descarta** y se vuelve a pedir (ver [Caché de lecturas](#caché-de-lecturas)); si no, `_apply` lo vuelca a `mapping`/`*_ref`.
4. **Se repinta** una vez, al final, si se aplicó algo — incluido cuando solo llegaron fallos, porque sus códigos tienen que salir en tecla. `_paint_current_screen()` resuelve la **pantalla activa** (no solo "Hoy": lo que sea que esté abierto) contra los datos que acaban de llegar (`core.screens.resolve_page`), la pinta (`renderer.render_page`), pinta encima los códigos de error **si la pantalla visible los usa** (los de hábitos solo en "Hoy"/"Hábitos"/una sección, los de logs solo en "Logs", los de tareas en "Hoy"/"Tareas"/un proyecto, los de plantillas solo en "Crear", los de etiquetas solo en "Cronómetros", los de TickTick solo en esa pantalla), y **re-registra** `deck.set_key_callback(...)` con un closure fresco.

Qué aporta cada lectura, y qué pasa si falla:

1. `get_habits()` (`Resource.HABITS`) — una sola petición; ya trae el progreso de hoy en `current_value`, no hay ninguna fecha que decidir en el cliente. Es la única cuyo éxito llama además a `key_map.update_mapping()` (hacerlo tras un fallo liberaría las teclas de hábitos que siguen existiendo). Falla → rojo en las teclas de hábitos.
2. `get_log_habits()` (`LOG_HABITS`) — los hábitos de solo registro (`LogHabit`, ver [Vista "Logs"](#vista-logs)). **No** toca el mapeo persistido: "Logs" no lo reutiliza (ver [Reparto de teclas](#reparto-de-teclas)). Falla → rojo en "Logs".
3. `get_tasks()` (`TASKS`) — solo pendientes y ya ordenadas. Las tareas no tienen mapeo propio: cada vista las reparte en tecla cuando le toca pintarse. Falla → rojo en las teclas de tarea.
4. `get_templates()` (`TEMPLATES`) — solo las de creación rápida, ya ordenadas por título. Cambian rarísimamente, pero como "Crear" relee siempre al entrar (`max_age_seconds = 0`), viajan con las tareas de esa pantalla. Falla → rojo en "Crear".
5. `get_timer_labels()` (`TIMER_LABELS`) — las etiquetas rápidas de cronómetro (ver [Vista "Cronómetros"](#vista-cronómetros)). **Sí** pinta rojo si falla: sin catálogo no hay nada que ofrecer.
6. `get_running_timer()` (`RUNNING_TIMER`) — el cronómetro en marcha ahora mismo, o `None`. Un fallo aquí **NO pinta tecla en rojo**: solo se pierde el resaltado de "cuál está corriendo", y el toggle sigue siendo correcto porque lo decide `rpc/timer_toggle` contra el estado real, no contra este valor cacheado.
7. `get_daily_totals()` (`DAILY_TOTALS`) — segundos acumulados hoy por id de tarea/etiqueta (`v_timer_daily_totals`). **Tampoco pinta rojo**: solo se pierde el total del día hasta la próxima lectura con éxito (la tecla sigue mostrando el nombre solo, nunca un número obsoleto).
8. `get_task_totals()` (`TASK_TOTALS`) — segundos acumulados de SIEMPRE por `task_id` (`v_task_timer_totals`). Mismo tratamiento que el anterior.
9. `Resource.TICKTICK` — tareas y proyectos de TickTick en la misma pasada, bajo un único código de error (ver [Vista "TickTick"](#vista-ticktick)). Sin token configurado ni siquiera intenta red: `AUTH` directo.

**Cada lectura falla por separado**: la que falla no toca su mapeo ni sus datos (se conservan los del ciclo anterior) y no afecta a las otras. Siempre que se aplique algo -- datos nuevos o codigos de error -- se llega a pintar y a re-registrar el callback, de modo que lo pintado y lo que hace cada tecla nunca se desincronizan.

**Reactivación de un proyecto Supabase pausado.** Un proyecto del plan gratuito se pausa solo tras ~1 semana sin tráfico: su subdominio de API deja de resolver por DNS, lo que `provider.supabase` traduce en el mismo `ProviderNetworkError`/`NET` que "la Pi no tiene red" — son indistinguibles desde el propio checkin. Al final de `_fetch_resources` (ya **fuera** de `screen_lock`, es una llamada de red que no toca pantalla ni mapeo), si cualquiera de las ocho lecturas de habits-core arrastra `NET` (solo esas: un `NET` de la API de TickTick no dice nada de Supabase), se lanza en su propio hilo `provider.keepalive.try_restore_active_project()`, que pide la reactivación a la Management API de Supabase (`api.supabase.com`, no PostgREST). Es una **credencial y una API distintas** de las que usa `provider/supabase.py`: requiere `SUPABASE_ACCESS_TOKEN` (Personal Access Token de la cuenta, no la clave publishable) en el `.env` — sin él, la función no hace nada y el daemon se comporta exactamente igual que antes de que este módulo existiera. `config.RESTORE_COOLDOWN_SECONDS` (30 min) evita repetir la petición mientras el proyecto sigue "despertando" (tarda uno o dos minutos; se confirma solo, en un ciclo posterior).

El estado que ve el callback son wrappers dict de una entrada (`habits_ref`/`tasks_ref`/`templates_ref`/`timer_labels_ref = {"value": {id: obj}}`, `running_timer_ref = {"value": RunningTimer | None}` — uno solo, no por id: como mucho hay un cronómetro corriendo — y `daily_totals_ref`/`task_totals_ref = {"value": {id: segundos}}`, igual que los primeros) precisamente para que el closure observe las actualizaciones de ciclos posteriores. Aun así, **el mapeo tecla→elemento solo es tan reciente como el último ciclo o la última navegación.**

**Al pulsar una tecla (`make_key_callback`):**

1. Reprograma **los dos** temporizadores de inactividad (`AUTO_RETURN_SECONDS` y `STANDBY_SECONDS`, vía `_reset_idle_timers`), sea cual sea la tecla. Si la pantalla activa es el stand by, la pulsación no hace nada más que despertar (ver [Stand by](#stand-by)).
2. Bajo `screen_lock`, resuelve la página activa (`core.screens.resolve_page`) y la pulsación contra ella (`core.screens.resolve_press`) a una `PressAction`.
3. Si la acción es de hábito o tarea (`"habit"`/`"habit_undo"`/`"task"`), **no se ejecuta todavía**: se arma un temporizador de `LONG_PRESS_SECONDS`. Si la tecla se suelta antes, se cancela y se ejecuta como una pulsación corta (pasos 4/5 de abajo); si el temporizador dispara con la tecla aún pulsada, se abre el menú de opciones del elemento en su lugar (ver [Menú de opciones de un hábito/tarea (mantener pulsado)](#menú-de-opciones-de-un-hábitotarea-mantener-pulsado)) y la liberación posterior de la tecla no hace nada. El resto de acciones (plantilla, cronómetro, navegación, teclado numérico) se ejecuta al presionar, sin esta espera.
4. **Hábito** (pulsación corta) → `provider.step(habit)`, **sin comprobar si ya alcanzó el objetivo**: la tecla nunca se bloquea, es la base quien decide el nuevo valor. Éxito → `habit.current_value = new_value` (mutación directa del objeto compartido con `habits_ref`) y `repaint()`: repinta la **pantalla activa entera**, optimista, sin refetch — la tecla pasa de blanco a gris en su misma posición, nada se recoloca (ver [Completar no hace desaparecer](#completar-no-hace-desaparecer)). `pending_requests` + `state_lock` (vía `_claim`/`_release`) descartan una segunda pulsación del mismo elemento mientras hay una en vuelo.

   **Deshacer un hábito** (`PressAction` de tipo `"habit_undo"`: booleano ya hecho en "Hoy"/"Hábitos", ver [Menú y pantallas](#menú-y-pantallas), también pulsación corta) → `provider.undo(habit)`. Éxito → la misma mutación optimista, con su `repaint()`, **y además una relectura de los hábitos por detrás** (`refresh_after_write(HABIT_RESOURCES)`, ver [Caché de lecturas](#caché-de-lecturas)): el valor que devuelve `habit_undo` es el del día, y en un hábito `weekly_quota` la vista pinta el contador de la semana, así que lo único fiable es releer. La mutación optimista se hace igualmente para que, si esa relectura falla, la tecla quede con el estado nuevo y no con el viejo. La reserva de `_claim` es el `habit_id`, así que un paso y un deshacer del mismo hábito tampoco pueden solaparse.
5. **Tarea** (pulsación corta) → primero `render_task_sending` (verde vivo + ✔, acuse de recibo inmediato), luego `complete_task(task)`. Solo cuando la base **confirma** (204), se muta `task.completed = True` (la tarea **se queda** en `tasks_ref`, ver [Completar no hace desaparecer](#completar-no-hace-desaparecer)) y se llama a `repaint()`: la tecla pasa a gris en su misma posición, nada se recoloca. Solo la siguiente lectura real de tareas la quita de la lista (completarla la deja caducada, así que basta con volver a entrar en la vista). Pulsar una tarea ya gris resuelve a `PressAction("noop")` (`core.screens.resolve_press`): no hay forma de revertir un cierre desde el deck.
6. **Plantilla** (solo en "Crear") → mismo acuse verde, luego `create_task(template)`. Al confirmar la base, la ocurrencia devuelta se **añade** a `tasks_ref` y se repinta: la plantilla se queda en pantalla (ahora en gris, y su tecla ya no hace nada) y la tarea nueva aparece en "Hoy"/"Tareas" sin esperar al siguiente ciclo. Se queda en "Crear", no navega: así se pueden encadenar varias.
7. **Cambiar la prioridad o hacer skip de una tarea** (dentro del menú de opciones de una tarea, `PressAction` de tipo `"task_set_priority"`/`"task_skip"`) → ninguna lleva el id de la tarea en el payload: se lee de `screen.entry_item_id` en el momento de ejecutar, se reserva con `_claim`/`_release` igual que cualquier otra escritura. `"task_set_priority"` llama a `set_priority(task, priority)`, éxito → mutación optimista de `task.priority` + `exit_item_options`. `"task_skip"` pinta primero el acuse verde (`render_task_sending`) y llama a `skip_task(task)`, éxito → la tarea sale de `tasks_ref` de inmediato (a diferencia de completar, ver [Completar no hace desaparecer](#completar-no-hace-desaparecer): omitir queda deliberadamente fuera de ese estándar, solo se llega aquí desde el menú de mantener pulsado, no con un tap normal) + `exit_item_options`. Fallo en cualquiera de las dos → tecla en rojo con el código, sin salir del menú. Ver [Menú de opciones de un hábito/tarea (mantener pulsado)](#menú-de-opciones-de-un-hábitotarea-mantener-pulsado).
8. **Cronómetro** (tecla de "Cronómetros", o la opción "Iniciar/Detener cronómetro" del menú de una tarea — mismo `PressAction("timer_toggle", item_id)` en los dos casos, ver [Vista "Cronómetros"](#vista-cronómetros)) → `orchestrator.press_timer_toggle` busca `item_id` primero en `tasks_ref`, si no en `timer_labels_ref`, y llama a `toggle_task_timer`/`toggle_label_timer` según dónde lo encontró. **Nunca mutación optimista**: la base puede parar un cronómetro distinto del que se pulsó, así que éxito → siempre relectura real de los cronómetros (`refresh_after_write(TIMER_RESOURCES)`), **sin tocar `screen.kind`** (se queda en el menú de opciones si venía de ahí, mismo criterio que "Ajustar el progreso" de un hábito real). No entra en `_HOLD_KINDS`: actúa al presionar, sin distinguir toque corto/largo. Fallo → tecla en rojo con el código, mismo patrón que el resto.
9. **Navegación** (abrir menú/Sistema, volver, elegir vista, paginar, abrir/cerrar el menú de opciones, apagar) → se delega en el dispatcher de `orchestrator.py` (`_dispatch_navigation`), que llama a `_enter_menu`/`_enter_system`/`_enter_view`/`_change_page`/`_exit_item_options`/`deck_keys.shutdown_pi`. `_enter_view` (entrar en una vista desde el menú) usa el mismo patrón `_claim`/`_release` que un hábito/tarea/plantilla, con una clave centinela fija, para no disparar dos refrescos por un doble toque.
10. `ProviderError` (en un checkin/cierre/creación/cambio de prioridad/toggle de cronómetro) → tecla en rojo con el código + entrada en `checkin_failures.log`.
11. Cualquier otra excepción → se trata como fallo de dispositivo: **nunca se muestra en tecla**, se registra en `device_errors.log` y dispara `session.reconnect()`. Los repintados van envueltos en `_safe_render` justo por esto. Como `reconnect()` reabre el deck a `BRIGHTNESS`, el bucle re-aplica `BRIGHTNESS_STANDBY` después si estaba suspendido: si no, un fallo de dispositivo encendería el deck sin que nadie lo haya pulsado.

No hay tecla de refresco manual: entrar en una vista desde el menú ya relee lo que esa vista necesite si está caducado (ver [Caché de lecturas](#caché-de-lecturas)), y el ciclo periódico se encarga del resto.

## Reparto de teclas

De las 15 teclas, `RESERVED_KEYS = {0, 5, 10}` nunca llevan hábito, tarea, plantilla ni entrada de menú — solo cambia *qué* se pinta ahí según la pantalla (ver [Menú y pantallas](#menú-y-pantallas)); quedan 12 (`AVAILABLE_KEYS`, ver `config.PAGE_SIZE`) que son el único espacio de contenido, en menú, en Sistema y en cualquier vista por igual.

Dentro de "Hábitos", que reutiliza el mapeo estable de hábitos (`core.screens._tiered_page_builder`), la página 0 sigue las mismas reglas de siempre:

- **Los hábitos van primero** y su tecla es estable: se persiste en `habit_key_map.json` y no se reasigna nunca mientras el hábito exista — **salvo la tecla 1** (`core.screens.KEY_HABITS_SECTIONS_SHORTCUT`), reservada de forma permanente para el atajo a "Secciones" (ver [Secciones](#secciones)): ningún hábito la ocupa nunca, ni en la página 0 ni en el sobrante.
- Lo que no cabe en la página 0 (antes se descartaba como `KFUL`) ya no se pierde: pasa a la página 1, 2... en el mismo orden, sin garantía de estabilidad entre ciclos ahí — es la red de seguridad, no el camino principal. Ver [Menú y pantallas](#menú-y-pantallas).

"Hoy", "Tareas", "Crear", "Logs" y "Cronómetros" no reservan nada para hábitos ni persisten tecla: paginan de cero, cada vez, la lista completa que les toque desde la tecla 1 en adelante (`core.screens._flat_page_builder`) — en "Hoy" primero TODOS los hábitos de hoy, hechos o no (por `order`), luego TODAS las tareas, pendientes o recién completadas (por prioridad/fecha); en "Tareas", todas las tareas; en "Crear", todas las plantillas (por título); en "Logs", todos los `LogHabit` (por `order`, ver [Vista "Logs"](#vista-logs)); en "Cronómetros", todas las `timer_labels` con `show_in_deck` (por `order`, ver [Vista "Cronómetros"](#vista-cronómetros)). Ninguna deja hueco al completar algo porque nada se filtra por completarse (ver [Completar no hace desaparecer](#completar-no-hace-desaparecer)): un hábito hecho o una tarea cerrada solo cambian de color, así que la tecla de cada una ya sale estable entre ciclos sin necesitar el mapeo persistido de "Hábitos". Una sección/proyecto (fijo o desde "Secciones"/"Proyectos", ver [Secciones](#secciones)/[Proyectos](#proyectos)) sigue el mismo criterio — nada desaparece de ellos solo por completarse — aunque ni siquiera pasan por `_flat_page_builder`: `core.screens._section_page`/`_project_page` paginan directamente.

Dentro de "Hábitos" los hábitos ocupan las teclas libres a partir de la 2 (la 1 es del atajo a "Secciones"); en "Hoy" la tecla de cada hábito/tarea depende de cuántos haya en cada momento (uno nuevo entra, uno omitido/archivado sale), pero no de si ya se completó.

Las tareas se pintan con el color de su prioridad (`deck/style.py`): **0 blanca, 1 verde, 3 amarilla, 5 roja**. No llevan icono, así que una tarea de prioridad 0 se ve igual que un hábito booleano pendiente — es una consecuencia asumida del esquema de color elegido, no un descuido.

## Teclas reservadas

| Tecla | Constante | Acción |
|---|---|---|
| 0 | `KEY_MENU` | Abre el menú principal desde cualquier pantalla (no-op si ya está abierto) |
| 5 | `KEY_PAGE_PREV` | Flecha "◀" si la pantalla activa tiene más de una página; gris neutro si no |
| 10 | `KEY_PAGE_NEXT` | Flecha "▶" si la pantalla activa tiene más de una página; gris neutro si no |

En el teclado numérico las tres se reinterpretan (salir/borrar/OK); en el menú de opciones de un hábito/tarea (mantener pulsado) la tecla 0 se reinterpreta como "Volver" y la 5/10 quedan vacías (ver [Menú de opciones de un hábito/tarea (mantener pulsado)](#menú-de-opciones-de-un-hábitotarea-mantener-pulsado)); y **en stand by ninguna hace lo de siempre**: cualquiera de las 15 se limita a despertar el deck (ver [Stand by](#stand-by)).

El apagado de la Pi ya no es una tecla fija: es el botón "Apagar" del submenú Sistema (menú → Sistema → Apagar), pintado en rojo de aviso para seguir distinguiéndose como acción destructiva.

### El submenú Sistema

Dos botones, en este orden: **"Suspender"** (tecla 1, azul de navegación) y **"Apagar"** (tecla 2, rojo de aviso). El orden es deliberado: la acción reversible se queda con la tecla más accesible y la irreversible no hereda la posición de la que se pulsa a menudo. El color hace el resto — el rojo sigue siendo exclusivo de "Apagar".

"Suspender" **no necesita ninguna regla `sudoers`**, al contrario que "Apagar": es una llamada USB al propio deck (`set_brightness`), no un comando del sistema. Lo de abajo aplica solo a "Apagar".

#### Apagado de la Pi

`deck.keys.shutdown_pi()` ejecuta `sudo -n shutdown -h now`. El servicio corre como `admin` **sin sudo**, así que hace falta una regla `NOPASSWD` en la Pi para que el comando no se quede pidiendo contraseña (el `-n` hace que falle rápido en vez de bloquear si la regla no está):

```bash
echo 'admin ALL=(root) NOPASSWD: /usr/sbin/shutdown -h now' | sudo tee /etc/sudoers.d/streamdeck-habits-shutdown
sudo chmod 440 /etc/sudoers.d/streamdeck-habits-shutdown
```

**Regla ya aplicada en la Pi desplegada: el botón apaga sin problema.** Si algún día hay que reinstalar la Pi desde cero o mover el servicio a otra máquina, hay que reaplicar esta regla a mano (requiere contraseña interactiva, no se puede por SSH no interactivo desde aquí) o el botón fallará silenciosamente y quedará solo en `device_errors.log`, sin señal en la tecla, igual que el resto de errores de dispositivo.

## Operar la Raspberry Pi

Hay acceso SSH sin contraseña (clave pública ya autorizada) desde esta máquina: `ssh admin@RP3-MotoComm-1.local`. Puedes lanzar comandos directamente en la Pi (logs, estado del servicio, reinicio, despliegue, verificación) sin depender del usuario.

La resolución mDNS del `.local` es a veces intermitente: si un comando falla con "Could not resolve hostname", **reintenta antes de darlo por caído**.

**Confirma con el usuario antes de un despliegue normal** (`deploy/deploy.sh` sin `--test`, que hace `git pull`) **o de tocar `SUPABASE_ENV`**, salvo que ya lo haya pedido explícitamente en el mismo turno: eso sí toca `main`/producción de verdad. La verificación previa (compilar/importar en un temporal) no afecta al servicio y no necesita confirmación.

**Un despliegue en modo `--test` NO necesita confirmación previa**: cuando el usuario pida un cambio de código en este repo, impleméntalo y, al terminar, llévalo tú mismo a la Pi con `deploy.sh --test` (ver [Probar código sin mergear](#probar-código-sin-mergear-deploysh---test)) sin esperar autorización — sigue siendo el árbol de trabajo local sin commitear, reversible con `git checkout -- .` en la Pi, y no toca `main` ni `SUPABASE_ENV`. Lo que sigue necesitando autorización explícita del usuario, siempre, es el **paso 4** de esa sección (`git commit`/`git push` y el despliegue normal posterior) — eso no cambia.

### Verificación previa al despliegue

Lo más parecido a un test disponible desde esta máquina. No toca el servicio en marcha: copia los `.py` a un directorio temporal en la Pi y los compila/importa con el venv real (Python 3.13.5, con todas las dependencias).

# Sintaxis (byte-compila, no ejecuta nada):

# Imports (detecta imports circulares, NameError, etc.). Seguro porque main() está bajo
# `if __name__ == "__main__"`, así que importar no arranca el daemon ni necesita un deck

tar cf - $(find . -name '*.py' -not -path './venv/*') | ssh admin@RP3-MotoComm-1.local \

### Probar código sin mergear (`deploy.sh --test`)

Para validar en la Pi un cambio del árbol de trabajo local **antes de commitear/mergear a `main`**, sin que `git pull` machaque el código de prueba. **Los pasos 1-3 no necesitan autorización del usuario** (ver la nota en [Operar la Raspberry Pi](#operar-la-raspberry-pi)): tras implementar un cambio que el usuario haya pedido, ejecútalos tú mismo para dejarlo probado en la Pi tal como quedó el código.

> **`--test` es un modo de despliegue, no una base de datos.** Lo único que significa es "reinicia con el código que ya hay en disco, sin `git pull`". La Pi sigue leyendo el proyecto Supabase que diga `SUPABASE_ENV` — normalmente `main`, o sea **producción**, y así debe quedarse. Son dos ejes independientes: `deploy.sh --test` ≠ `SUPABASE_ENV=test`. Ver [Cambiar de proyecto Supabase](#cambiar-de-proyecto-supabase-main--test) para cuándo (no) tocar el otro eje.

1. **Copiar** el árbol de trabajo (solo versionado + nuevos no ignorados; nunca `.env`, `venv/`, logs ni `habit_key_map.json`) sobre `/opt/streamdeck-habits`:

   ```bash
   tar cf - $(git ls-files -c -o --exclude-standard) | ssh admin@RP3-MotoComm-1.local 'tar xf - -C /opt/streamdeck-habits'
   ```

   Deja el árbol git de la Pi "sucio" respecto a `main`, pero es reversible. Al venir de Windows los ficheros llegan con CRLF (inocuo para Python; `.gitattributes` fuerza LF en los `.sh`/`.service` para que los scripts no se rompan).

2. **Reiniciar** con el código copiado, sin `git pull`:

   ```bash
   ssh admin@RP3-MotoComm-1.local 'bash /opt/streamdeck-habits/deploy/deploy.sh --test'
   ```

3. **Observar** que arranca limpio: PID nuevo estable, sin errores en el journal ni en `checkin_failures.log`/`device_errors.log`, y comportamiento correcto en el hardware.

4. **Si va bien** → commit + push a `main`; luego despliegue normal (`deploy/deploy.sh` sin `--test`, ver abajo) para que la Pi quede en `origin/main` con el árbol limpio.
   **Si va mal** → en la Pi `git -C /opt/streamdeck-habits checkout -- .` (restaura `main`) y `deploy/deploy.sh --test`. Si el código de prueba llegó a crashear en bucle y systemd lo dejó parado, arrancarlo de nuevo sí necesita sudo: `sudo systemctl start streamdeck-habits.service`.

> **El paso 4 lo autoriza el usuario, siempre.** Esta sección describe el procedimiento; **no** es permiso para ejecutarlo. **Nunca hagas `git commit` ni `git push` sin que el usuario lo pida explícitamente en ese momento**, por muy terminado y verificado que esté el trabajo. Que un plan aprobado liste "commit + push" entre sus pasos tampoco cuenta: aprobar el plan aprueba el trabajo, no la publicación. Al acabar, deja los cambios en el árbol de trabajo, resume qué cambió y pregunta. Si el usuario contesta algo asi como "despligue final" se ejecutará el paso 4: codigo a main y despliegue en la pi con el codigo limpio recien traido de lo que acaba de llegar a main.

**No dejes el paso 4 a medias.** Un `--test` que "fue bien" pero nunca se cerró con el despliegue normal deja la Pi con el árbol sucio y por detrás de `origin/main` indefinidamente — el servicio sigue corriendo con lo que haya en disco (puede coincidir con `main` por casualidad, o no) y nadie se entera hasta que alguien compara `git status`/`git log` a mano. Verificarlo cuesta un comando: `ssh admin@RP3-MotoComm-1.local 'cd /opt/streamdeck-habits && git status --short && git log --oneline -1'` debe salir vacío y en el mismo commit que `origin/main`. Si el usuario no autoriza el commit, **avisa de que la Pi queda así** en vez de resolverlo publicando por tu cuenta.

### Cambiar de proyecto Supabase (main / test)

Esto es **otra cosa** que el [despliegue en modo `--test`](#probar-código-sin-mergear-deploysh---test): aquel elige *qué código* corre en la Pi, este elige *contra qué base* habla. Se combinan libremente y lo normal es probar código nuevo (`--test`) contra `main`.

**Cuándo apuntar la Pi a `test`:**

- Cuando el cambio **toca la base**: una migración nueva en `../habits-core`, una vista o una RPC modificada, un `grant` que falta… Ahí no es opcional. Es el **paso 3** del proceso obligatorio que vive en `../habits-core/CLAUDE.md` → "El proceso de todo cambio de base de datos" (primera sección del fichero), y que resumido es: `develop` → PR a `test` → **probar aquí, en el deck, contra el proyecto de test** → PR a `main` → despliegue normal de la Pi y `SUPABASE_ENV` de vuelta a `main`. La rama `test` de `habits-core` es la que despliega a `habits-core-test`; `develop` es la de trabajo y no despliega sola. Ese fichero manda: si esto y aquello discrepan, gana `habits-core`.
- Cuando el usuario lo pida explícitamente.

**Cuándo no** (o sea, casi siempre): si el cambio es solo de funcionalidad del daemon — una vista nueva, un color, otra forma de repartir teclas, una pulsación que llama a una RPC **que ya existe y ya tiene su `grant`** —, no hay nada del contrato que validar y se prueba contra `main` como cualquier otro uso normal del deck. No cambies `SUPABASE_ENV` por tu cuenta ni lo ofrezcas como paso previo "por seguridad": escribir en producción es exactamente lo que hace el usuario cada vez que pulsa una tecla.

Si acabas apuntando a `test`, **devuélvela a `main` al terminar**: es fácil dejarla ahí y que el deck siga pintando datos de mentira días después.

**`habit_key_map.json` es único y no distingue de proyecto.** Cambiar `SUPABASE_ENV` no lo vacía ni lo cambia de fichero: al saltar a `test`, los hábitos de `main` que no existan ahí liberan su tecla y los de `test` reclaman las libres; al volver a `main`, sus hábitos vuelven a reclamar tecla **desde cero**, sin garantía de que sea la misma de antes de saltar a `test`. No es un bug — `update_mapping` hace exactamente lo que documenta ("nuevo hábito reclama la más baja libre") — pero conviene saberlo antes de sorprenderse de que un hábito cambió de sitio tras una prueba en `test`. Confirmado el 2026-08-05: al volver a `main` tras probar la pantalla "Crear", "Gym" reclamó la tecla 7.

**Pendiente de revisar**: si esto molesta en la práctica, la solución sería separar el mapeo por entorno (`habit_key_map_main.json` / `habit_key_map_test.json`, o una clave por `habit_id` que incluya el proyecto) en `core/key_map.py`. No implementado todavía — de momento se asume el barajeo tras cada préstamo a `test`.

Hay dos proyectos Supabase activos, cada uno con su propia base (esquema
identico, datos independientes):

| Alias | Proyecto | ref | URL |

| `main` | `habits-core` (produccion) | `ufyzpixnhrsltoxdqihn` | `https://ufyzpixnhrsltoxdqihn.supabase.co` |

### Despliegue

```bash
ssh admin@RP3-MotoComm-1.local "bash /opt/streamdeck-habits/deploy/deploy.sh"
```

`deploy.sh` hace `git pull` y mata el proceso principal para que systemd lo relance por `Restart=on-failure` con el código nuevo — **sin sudo**, por eso funciona en SSH no interactivo. Con `--test` hace lo mismo sin el `git pull`.

- **No instala cambios de la unit de systemd.** Si tocas `deploy/streamdeck-habits.service`, cópialo a mano a `/etc/systemd/system/` con `sudo` + `daemon-reload` + `restart`.
- Existe un alias `habits-update` en el `~/.bashrc` de la Pi para uso interactivo, pero **no funciona desde `ssh host "habits-update"`**: el `.bashrc` de Debian corta la ejecución al inicio si el shell no es interactivo (`case $- in *i*) ;; *) return;; esac`), así que el alias nunca llega a definirse y falla con `command not found`. Usa siempre la ruta completa al script.

### El deck se queda colgado tras varios reinicios seguidos (`Failed to write feature report`)

**Síntoma**: el servicio entra en **bucle de reinicio** y el journal repite esto, con un PID nuevo cada pocos segundos:

```
File "/opt/streamdeck-habits/deck/session.py", line 63, in open
    deck.reset()
StreamDeck.Transport.Transport.TransportError: Failed to write feature report (-1)
python: ../../libusb/os/threads_posix.h:46: usbi_mutex_lock: Assertion `pthread_mutex_lock(mutex) == 0' failed.
```

`systemctl is-active` responde `activating`, el `MainPID` es `0` y el contador de reinicios sube sin parar.

**Qué NO es**: no es el código que acabas de desplegar. Revienta en `session.open()` → `deck.reset()`, o sea en la **primera escritura USB**, antes de tocar datos, red o pantalla — el deck sigue apareciendo en `lsusb`, pero rechaza cualquier escritura. Antes de buscar el fallo en un cambio tuyo, comprueba si la traza es esta.

**Causa**: el dispositivo se queda atascado a nivel HID después de **encadenar varios reinicios bruscos**. `deploy.sh` reinicia matando el proceso con `kill -9` (es lo que le permite funcionar sin sudo), y si eso pilla una transferencia USB a medias, el deck se queda en ese estado. Con un despliegue suelto no pasa; se vio haciendo tres seguidos en diez minutos (`--test`, `--test`, despliegue normal).

**Arreglo**, sin sudo y sin tocar el cable:

```bash
ssh admin@RP3-MotoComm-1.local '/opt/streamdeck-habits/venv/bin/python /opt/streamdeck-habits/scripts/usbreset.py'
```

Manda el ioctl `USBDEVFS_RESET` al nodo del dispositivo (equivale a desenchufarlo y enchufarlo). No hace falta parar el servicio: systemd sigue reintentando y el siguiente intento, unos segundos después, abre el deck ya sin problema. Confírmalo con `systemctl is-active` (debe decir `active`) y con un `MainPID` que se mantenga.

**Cómo evitarlo**: no encadenes reinicios sin necesidad. Un cambio que solo toca documentación, `scripts/` o cualquier cosa que el daemon no importe **no necesita reiniciar**: basta con `ssh admin@RP3-MotoComm-1.local 'git -C /opt/streamdeck-habits pull'`, sin `deploy.sh`.

### Disposición en la Pi

`config.py` fija `BASE_DIR = "/opt/streamdeck-habits"` y el shebang de `orchestrator.py` apunta a `/opt/streamdeck-habits/venv/bin/python` (Python 3.13.5). **No hay override por variable de entorno: trata `BASE_DIR` como fijo.** Junto al código se espera (todo gitignored salvo `.env.example`):

- `.env` — credenciales de **ambos** proyectos (`SUPABASE_URL`/`SUPABASE_PUBLISHABLE_KEY` para main, `_TEST` para test) más `SUPABASE_ENV` para elegir cuál usa `SupabaseProvider.__init__` (vía `python-dotenv`) — ver [Cambiar de proyecto Supabase](#cambiar-de-proyecto-supabase-main--test) — más, aparte y sin relación con lo anterior, `TICKTICK_ACCESS_TOKEN` para `TickTickApiProvider` (ver [Vista "TickTick"](#vista-ticktick)); opcional, su ausencia solo pinta `AUTH` en esa pantalla, el resto del daemon sigue igual
- `habit_key_map.json` — mapeo `habit_id -> key_index`, se crea y actualiza solo
- `pinned_sections.json` — lista de nombres de sección fijados como botón del menú principal (ver [Secciones](#secciones)), se crea y actualiza solo desde el propio deck
- `pinned_projects.json` — lista de nombres de proyecto fijados como botón del menú principal (ver [Proyectos](#proyectos)), se crea y actualiza solo desde el propio deck
- `checkin_failures.log` — JSON-lines de escrituras fallidas hacia Supabase: checkins de hábito, cierres de tarea, creaciones desde plantilla y toggles de cronómetro (errores de API, tecla en rojo); el campo `kind` distingue `"habit"` / `"task"` / `"template"` / `"timer"` / `"ticktick"` (esta última hacia la API de TickTick, no hacia Supabase)
- `device_errors.log` — texto plano de fallos del propio dispositivo (nunca se muestran en tecla)

## Ejecutar y dependencias

No hay `requirements.txt` ni lockfile: los cuatro imports de terceros se instalan a mano en un venv.

```bash
pip install streamdeck python-dotenv requests Pillow
```

- `python orchestrator.py` — daemon principal (requiere una Stream Deck real conectada y un `.env` válido)
- `python scripts/test_hw.py` — smoke test de hardware: enumera el deck, imprime modelo/serie/firmware, registra pulsaciones crudas
- `python scripts/toggle_test.py` — smoke test visual: alterna cada tecla entre azul y verde al pulsarla, sin llamadas de red
- `python scripts/usbreset.py` — resetea el deck por USB cuando se queda colgado a nivel HID y el servicio entra en bucle de reinicio (ver [El deck se queda colgado tras varios reinicios seguidos](#el-deck-se-queda-colgado-tras-varios-reinicios-seguidos-failed-to-write-feature-report)). Es el único que NO usa la librería `StreamDeck` ni necesita que el deck responda: habla directamente con el nodo USB

Los tres primeros necesitan que la librería `StreamDeck` (python-elgato-streamdeck) tenga acceso al dispositivo USB físico; `usbreset.py` solo necesita el nodo de `/dev/bus/usb` (por eso sirve justo cuando la librería ya no puede abrirlo). Los cuatro solo tienen sentido en el hardware objetivo.

Para pintar el emoji del nombre de un hábito como icono a color hace falta además la fuente del sistema `fonts-noto-color-emoji` (paquete Debian, no de Python): `sudo apt install fonts-noto-color-emoji` — requiere sudo interactivo, no se puede instalar por SSH no interactivo desde aquí. Si falta, `deck/primitives.py::_emoji_font()` devuelve `None` y la tecla simplemente no pinta icono: **se degrada, no falla**.

## Estilo y convenciones

El estándar está en `pyproject.toml` (ver también `.claude/skills/SKILL_Python_Code_Style_&_Documentation.md`):

- **`ruff`** — lint + formato (línea 120, comillas dobles, isort/pyupgrade/bugbear/simplify): `ruff check --fix .` y `ruff format .`
- **`mypy`** — comprobación de tipos (`target py313`; `StreamDeck.*` con `ignore_missing_imports` porque no publica stubs): `mypy .`
- **Type hints** en todas las APIs públicas, con `from __future__ import annotations` al principio de cada módulo (evaluación diferida: la anotación nunca se evalúa en runtime, así que es segura aunque apunte a algo no importado).
- **Docstrings estilo Google** (Args/Returns/Raises) en clases y funciones públicas.
- **Comentarios y mensajes de log en español.**
- **Todos los `print` con `flush=True`**: esto corre como servicio en segundo plano sin buffer (logging estilo journald/systemd).
